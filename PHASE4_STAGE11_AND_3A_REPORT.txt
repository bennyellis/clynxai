  After:  1 credible (iPhone 16e, justified); 6 unverified (note only); 1 short form; "13th" no longer an identifier. Wasted lookups: 0.
  The nine cases:
    "13th"  (Friday the 13th in an Xbox Series X bundle)  -> ignored: an ordinal is never a model number
    "16e"   iPhone 16e vs entry iPhone 16                  -> CREDIBLE: the Database already has an "iPhone 16e" entry. The listing is priced under that entry by name
    "o1766" Xbox Series S 512GB ... O1766                   -> unverified: the code appears nowhere else
    "t3586" Xbox Series S 1TB Black ... T3586               -> unverified
    "jtm7"  Xbox Series S JTM7-CE                            -> unverified
    "z7ux"  Xbox Series S Console Z7UX                       -> unverified
    "d6306" Xbox Series S White D6306                        -> unverified
    "2k27"  NBA 2K27 with an Xbox Series S                   -> unverified (and games that only name the console in brackets can never vouch for their own code)
    "ps5"   Playstation 5 PS5 ... vs "PlayStation 5 Slim"    -> short form of the name: not an extra at all
  What "unverified" does: it neither claims the match is exact nor suppresses the deal. The listing keeps its verdict; a "high" confidence is shown as
  "medium" with the note "the title also states Z7UX, which nothing confirms is a model or version marker". No research is started for it, and its code is
  never put in a WatchCount query.
  Evidence rules (all category-free): a code is credible only if (a) a Database entry that carries it also says everything the matched entry says, or is a
  related model of the same family; (b) the photo analysis of THIS listing names it; or (c) two or more documents from different sources (other sellers'
  listings, other entries, reference-photo titles) carry it next to the product's own words. The same seller repeating a code counts once. Documents that
  merely mention the product ("Game (Console)", "Cable for Console") do not vouch for the mentioning item's code.

4. STAGE 3a: SCHEMA AND RELATIONSHIP DESIGN
-------------------------------------------
  Switches (config.json, both false): identityFoundation.schema creates the tables when the Database is opened; identityFoundation.backfill (needs schema)
  fills them a minute after startup. Off: no table exists and no code runs. Only the Store opens the foundation; no scoring, matching or valuation module reads it.
  Tables (no FOREIGN KEY to any existing table, nothing existing altered):
    identity_meta        key/value (schema version, backfill phase and cursor, timestamps)
    product_identity     one row per product: level (exact / line / unknown), identity_key, confidence, attributes_json, unresolved_json, evidence_json, source_hash
    identity_terms       (product_id, term, kind) with an index on term: the candidate index
    product_relations    from, to, relation, role, status, confidence, evidence_json, ambiguity_json, decided_at/by/note; unique per (from, to, relation)
    product_aliases      alias text/norm -> product, status, source, confidence, evidence_json, decided_at/by/note; unique per (alias, product)
    listing_identity     per listing: its own best-fit entry beside the link it already has, level, confidence, extras (credible / unverified / dismissed), unresolved
    identity_audit       append-only: who/what/when, before and after of every proposal, decision, revert and removal
  Identity representation (category-agnostic): each attribute has a kind (word, code, capacity, number, host), a value, a source (name, filed title, listing
  title, photo analysis, user), a confidence and a weight ("likely-defining" or "unknown": what an attribute is worth in telling products apart is NOT decided
  yet, that needs price evidence). Level: "exact" when the name states a model, version, size or capacity identifier; "line" when it only describes;
  "unknown" otherwise. Confidence is uncalibrated and used for ordering only. The bracketed part of a name ("(Nintendo 3DS)") is stored as a separate "host".
  Relations (all start as CANDIDATE; nothing in the app acts on them):
    references     one product names another as what it goes with or runs on (brackets, "for", "with"): a game for a console, a cable for a console. NOT the same
                   product, never a parent. Role says how ("for", "with", "includes").
    narrower-than  the first states more than the second. Always stored with its ambiguity: it could be a more specific version OR an accessory, component or bundle.
    same-as        identical wording, or equal only if a short form means the longer word (lower confidence). Never created between a referencing product and its host.
  Aliases: short forms found in titles filed under a product ("ps5" under "PlayStation 5 Slim") are stored as candidates with their support.
  Decisions: decideRelation / decideAlias record who and why; backfill never touches a decided row; revertAudit restores the previous state (only the most
  recent change to an item, otherwise it refuses); exportDecisions then drop() removes the whole foundation; deleting a product removes its identity rows and
  keeps what they were in the audit log. There is NO code path that promotes a candidate without an explicit call.
  Indexed candidate retrieval: through the term index only (EXPLAIN shows index use), skipping terms that nearly every product has; no table scan.
  Backfill: phases products -> relations -> aliases -> listings; each step is time-boxed (20 ms by the app), one transaction, saves its cursor, every write is an
  upsert, so it can be stopped at any moment and resumed.
  Not in 3a (as instructed): no resolver for live selection, no merging, no alias promotion, no revaluation, no UI.

8. REMAINING RISKS AND LIMITATIONS
----------------------------------
  - Candidates are only candidates. The classifier is heuristic: brackets can be an edition or a repeated name; brand-level entries create low-value relations; some alias
    candidates are wrong. Nothing may be promoted automatically; a review step is needed before anything is used.
  - First sightings of a genuinely new model with no sibling entry, no other listing and no photo-analysis name stay "unverified" (about 7 of 74 on your data).
  - The evidence index counts documents; a seller using different titles with the same invented code on several accounts could appear as two sources.
  - Identity "level" and "confidence" are uncalibrated; attribute weights are unknown until price evidence is used (Stage 5).
  - The Database copy is dominated by video games; accuracy outside them is unproven on real data.
  - Backfill spikes: occasional disk-commit stalls of 100-270 ms (about 2% of steps at 10,000 products) in a one-off background job.
  - Existing mixed entries are NOT repaired; this stage only records evidence. The relations table can be large for big libraries (about 0.12 per product here).
  - Cloud sync: the new tables are local-only and not synced; the server and other devices are unaffected.
  - Scratch data on this PC: C:\Users\biggt\ClynxDbCopy (your copy), ClynxShadowOutput, ClynxShadowOutput_run1, ClynxShadowOutput_stage11, ClynxShadowOutput_stage3a and
    ClynxShadowOutput_stdout* contain your product names and listing titles. Please delete them when you no longer need them.

HOW TO SWITCH IT ON (only when you decide to; it is off now)
-----------------------------------------------------------
  Close Clynx, make a backup copy of your data folder's scout.db, then in your user folder's config.json add
      "identityFoundation": { "schema": true, "backfill": true }
  and start Clynx. To undo: set both to false (the tables stay but nothing uses them); to remove them entirely a drop() is available and tested on the copy.
  Do not enable it on the live Database until you have authorized that separately.
