1. ARCHITECTURE: FROM MARKETPLACE PHOTO TO IDENTITY (src/main/identityResearch.ts)
 1 Observe the photos with NO seller words (visualProfile.OBSERVE_PROMPT; the observer takes only the images).
 2 Structured observation: object kind, legible brand, colours, artwork described in words, features, limits (glare, one angle).
 3 Candidate families come from the knowledge graph (a maker visible on the item or named in the title; the title only suggests where to look).
 4-6 Models and discriminators for that family come from the graph (what tells them apart, each with an evidence state).
 7 Targeted second look: only the questions that separate the candidates, with fixed answer options and "not_visible".
 8 Elimination: a photographed answer rules a model out only if the discriminator's evidence may do so (observed/researched/verified/owner_asserted). "not_visible" rules nothing out. Inferred discriminators never eliminate.
 9 Most specific SUPPORTED identity: one model only if one remains; otherwise the remaining models are listed as undecided. Model facts are labelled "inferred" (from photographed features) or "researched" (tied by an edition source), never "verified" from a photo.
 Edition: if distinctive artwork is seen, searches are built from what is SEEN ("nintendo yellow handheld special edition cartoon face"), sources are read (official first), edition names are extracted from the text (no list of franchises or characters), kept only with 2 independent sources or an official/specialist one, matched to the colours and artwork seen, and a theme classifier (AI, validated against the source text) links franchise and character. Factory authenticity is always reported as unverified (aftermarket shells exist).
 10-11 Condition and comparable matching are the existing pipelines (conditionEvidence, compIdentity).
 12 Everything learned is written to the knowledge graph (kg_* tables), never to the Library.
 Integration with the live scan: when a listing's identity is in doubt (low-confidence product check, or an item the Library has never seen), scrapeEngine calls onIdentityDoubt; index.ts runs the web research (productKnowledge, switch beta13.webKnowledge) and the observation pipeline (visualService, switch beta13.visualResearch). BOTH ARE SHADOW MODE: they record what they WOULD conclude in AI Activity ("Worked out what an item is from its photos", "Researched a product on the web", "Checked a model name against the maker's lineup") and change no filing, price, alert or Library entry. Rationed (4-6 per hour), skipped in Save-credits mode, never block a scan.
 Evidence states (evidenceKinds.ts): observed, seller_reported, researched, verified, inferred, owner_asserted, unknown. A seller's claim stays seller_reported; marketplace-only sources can never exceed that; an official source is needed for "verified"; conflicting claims make an entry "disputed" and are kept. owner_asserted is an addition to your list: it labels facts you supplied (the 3DS layout facts), may rule candidates out, and is upgraded only when an official source is actually read.

2. RESEARCH IMPLEMENTATION
 Search provider actually used: DuckDuckGo (two forms) then Bing, both keyless, through the existing evidence reader that detects bot checks and backs off. Brave Search API is used first when BRAVE_SEARCH_API_KEY is in .env. GOOGLE WAS NOT USED: Google's results page blocks automated requests, and its Programmable Search JSON API is closed to new customers, new engines can only search up to 50 chosen sites, and the API ends 2027-01-01 (secondhand sources, not Google's own docs). The Google backend code remains and works only for an account that already has a whole-web engine.
 The OpenAI model orchestrates: it proposes human-like searches, summarises, sorts themes; every fact it supplies is checked against the page text before it is kept.
 Source-backed discovery is demonstrated ONLY against fake pages (identityResearch.test.ts: the Pikachu Edition is found from text, tied to "New Nintendo 3DS XL", themed on Pokémon/Pikachu, an AI-invented "Digimon" is discarded). It has NOT been demonstrated on real pages.

5. DAMAGE DETECTION
 Implemented: vision prompt now carries explicit not-damage rules (glare, reflections, protectors, shadows, seams, patterns), an optional normal-appearance description from the knowledge graph (only when established), area coverage; merge logic states "possible damage" (low confidence), flags undisclosed damage, keeps a seller report the photos do not show, adds AREA_NOT_PHOTOGRAPHED ("Not photographed: back. Damage there cannot be ruled out."), and says photos show appearance only (phones: not activation lock, carrier status or battery health). The same defect in text and photos is ONE defect (tested: same deduction as one source). Valuation integration is the Beta 13 shadow-mode path (conditionEvidence, default shadow); no financial behaviour was switched on.
 Tested: the merge/valuation logic (54 checks). NOT tested: whether a real model sees a cracked back glass, a chipped corner, a broken hinge, or mistakes a reflection for a crack. No real examples, no measured false-positive rate.

7. LIBRARY FEATURES
 Automatic folders are virtual (category + family path), so renames and pictures are stored against the full path (folder_meta) and the original path words stay the identity: new products arriving on the path land in the renamed folder, a research refresh does not undo the name, and navigation memory keeps working. Rename/delete/thumbnails are available in the folder tile menu and the folder header menu (Database > Library), and in chat (library_op: renameAutoFolder, deleteAutoFolder, setFolderThumbnail, restoreFolderThumbnail, generateFolderThumbnail, undo; library_list: autoFolders, history). All of them run the same backend as the menu.
 Delete: "Move contents to the parent folder" or "Move the folder and its N products to the Trash" (asks first), cancel; undo restores; the Trash keeps 30 days; moved products are locked from re-organisation by research. Top-level categories cannot be renamed or deleted this way. Sibling name clashes, empty/over-long names and ">" are refused.
 Thumbnails: provenance ai_generated / auto / user_upload / user_selected / placeholder; a person's choice (or a generation they asked for) is locked and never replaced; "Use automatic pictures again" clears it. The prompt is built from the whole path ("Video Games & Consoles > Nintendo > Consoles" = Nintendo console hardware, avoid game cases, discs, controllers). Automatic generation: sub-folders only (brand top folders keep their logo), 3 a day (config folderArt.perDay), 10 a day for requests, once per folder (a failed try waits a week), never because the Library opened, off in Save-credits mode. The old web-photo fetch for sub-folders (which could keep a game's artwork on a console folder) is retired. Without generation, a photo of one of the folder's own products is used only if it is the right kind (console folder never takes a game); otherwise a placeholder.
 Demonstrated on a real on-disk store: rename persists across close/reopen and research refresh; upload, choose, restore; delete both ways with undo; chat rename and confirmation for delete-with-contents. NOT demonstrated: the screens themselves, a real generated image, a real restart of the app.

ADDENDUM - OPENAI WEB SEARCH (built after this report; version 0.3.0-beta.15)
 What: OpenAI's web search as an OPTIONAL first-choice engine for hard research (claim checks, edition research, knowledge research, observation research). Not Google. Off by default (config.json beta13.openaiSearch). Used first, then Brave/DuckDuckGo/Bing; it declines itself when off, in Save-credits mode, over its hourly limit (default 12, config openaiSearchPerHour) or after a failure (left alone for 5 minutes; 30 minutes when the model/tool is not available to the key or the server has it off). The cited pages become ordinary search results (each with the sentence it was cited for); Clynx still reads the pages and applies its two-source / official-source rules.
 Route: your own key goes straight to OpenAI's Responses endpoint; otherwise Clynx Cloud's new POST /ai/search. The server route takes ONLY a phrase and builds the whole provider request itself (one web_search tool, fixed model AI_SEARCH_MODEL default gpt-4.1-mini, capped answer, nothing stored), returns only {answer, citations}. OFF until the server owner sets AI_SEARCH_ENABLED=true; counted as one request against the plan's daily allowance; the per-search fee (AI_SEARCH_FEE_USD, default 0.03, an ESTIMATE) is reserved before the call and recorded; refused by the emergency stop, spending ceilings, rate limits; provider failures cost nothing and are not leaked.
 Verified: the pure request/parse code and the app backend/fallback logic (20 checks, fake network); the server route against a REAL Postgres and Redis with a fake OpenAI (11 tests: off by default, auth, clamping so a customer cannot choose model/tools/prompt, metering with the fee, plan quota, spending ceiling, emergency stop, provider failure). NOT verified: that OpenAI's web_search tool accepts this request and returns citations in this shape for the chosen model, and its real per-search price. One real call settles both: set the flag, ask the chat "is the RTX 4080 Ti a real model?", and look at AI Activity (kind "web search") and Activity decisions.
 Server tests in this sandbox: 328 pass; 6 fail the same way on the code BEFORE this change (5 AI-proxy tests need an OpenAI key in the test environment, and pass when one is set; 1 release-upload path test fails on Linux).
