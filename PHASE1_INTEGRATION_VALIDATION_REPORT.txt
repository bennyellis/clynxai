CLYNX: PHASE 1 INTEGRATION VALIDATION REPORT
============================================
Question: does the committed Phase 1 work actually behave in the REAL Electron app, not just in unit tests?
Method: the real built app (out/main + out/preload + out/renderer) was started by a test driver (Playwright's Electron support) inside a
throwaway sandbox, with its own user-data directory, its own per-user data folder and database, its own browser profile, and a fake cloud
server on 127.0.0.1:18787. Your real database, settings, session files, browser profiles and Facebook logins were never opened.

Bottom line
  - The real app starts, logs in, restores its session, loads/saves config, recovers from damaged config/session/database files without
    ever discarding the original, and shows the new notices and buttons. All new IPC handlers answer.
  - The validation FOUND 3 REAL DEFECTS in my Phase 1 work. They are fixed, covered by new regression tests that fail without the fix, and
    committed (b26982a). Details in section 3. One older bug unrelated to Phase 1 was also found and NOT changed (section 4).
  - Live Facebook behaviour was NOT verified. Everything Facebook-related ran against mocked pages (section 2).
  - Deal-quality code is byte-for-byte unchanged since the Phase 1 checkpoint, and its saved data works end to end in the real app.

2. WHAT WAS SIMULATED (and what that means)
-------------------------------------------
  - The cloud server: a fake on 127.0.0.1 that accepts any register/login/refresh and answers sync calls with empty lists.
  - Facebook: EVERY facebook.com request of the scan browser was answered by a mock page (healthy Marketplace page, login page, login wall,
    checkpoint page, connection refused). The scan engine, Playwright, real headless Google Chrome and the real DOM were used, so the page
    classification, the cycle logic, the notices, the buttons and the phone-push path ran for real; only Facebook's answers were fake.
  - The phone push target: a local mock of ntfy on 127.0.0.1:18788.
  - The databases: synthetic, generated by the tests.
  - Disclosure (containment): in my first T5 runs the mock answered "expired session" with an HTTP redirect. Chrome follows a fulfilled
    redirect inside the browser WITHOUT asking the mock again, so for those runs the sandbox's Chrome (a brand-new profile that had never
    logged in; no cookies, no credentials, nothing of yours) anonymously loaded Facebook's public login page and public /checkpoint URL from
    the real facebook.com, plus one blocked request to static.xx.fbcdn.net. No account was involved and nothing was submitted, but "mocked
    only" was not true for those runs. I noticed it from the page text in the log, replaced redirects with in-page redirects, and added a
    second barrier (the browser cannot resolve ANY host name, so nothing can leave even if a route is bypassed). The final T5 run (21 of 21)
    and every number above come from the contained setup; it also checks that no real Facebook page text and no DNS-blocked page ever
    rendered. The other tests never started the scanner, so they made no Facebook requests at all; I did not monitor other hosts the app
    itself might contact (for example on startup), only that the fake cloud saw just the expected calls.
  - Real data safety: a size and modified-time fingerprint of 9,460 paths of your real data (project data folder with the 544 MB database,
    browser profiles, config/session/settings files, and the AppData folders for Clynx and Marketplace Scout) taken before and after: 0 added,
    0 removed, 0 changed. Your Clynx was not running during the tests. File contents were never read for this check.


3. DEFECTS FOUND IN PHASE 1 BY THIS VALIDATION (all fixed, regression-tested, committed in b26982a)
---------------------------------------------------------------------------------------------------
 #1 Database recovery could fail and trap the user on "Loading..."   [store.ts, dbIntegrity.ts]
    Case: a valid SQLite file whose structure the app cannot use. The Store constructor threw halfway but left the database open; on Windows
    an open file cannot be moved, so quarantine failed with EBUSY and the login call rejected. The original was not lost (a copy had been made)
    but the user was stuck. Fix: the Store now closes its database when setup fails. Unit test added (fails with EBUSY without the fix,
    passes with it); the real-app case [c] now passes.
 #2 The Facebook-logout notice could flap and re-send the phone push every cycle   [scrapeEngine.ts]
    Case: Marketplace's front page loads fine but the page the cycle then opens is a login wall. The quick login check cleared the notice, the
    cycle raised it again, and the phone got a push every cycle (8 pushes in the test). Fix: only the check made after a location is opened
    can clear it, and the account stays "logged out" until then. Unit test added (fails without the fix).
 #3 A dropped connection did not raise the "can't reach Facebook" notice   [scrapeEngine.ts]
    A cycle where no page could be opened was recorded as a quiet success that found nothing, so the notice and the backoff never triggered
    in the most common failure. Fix: a cycle in which every location failed to open now counts as a failed cycle (the loop then backs off
    and, after 3, tells the user). Unit tests added for one location, several locations, and "connection fine but nothing found" (not a failure).
 Honest correction to my Phase 1 report: its limitation list did not say #3 existed; the Phase 1 claim that a dropped connection is reported
 was only true when the first login check itself threw.


4. FOUND, NOT CHANGED (outside Phase 1, per "no unrelated changes")
-------------------------------------------------------------------
  - Clicking the window's X on the LOGIN screen does nothing (also in the pre-Phase-1 build): the close request is handed to Config.tsx, which
    is only mounted after login, so nothing answers it. A logged-out user cannot close the app from the window. (Source: index.ts
    mainWindow.on("close") sends app:closeRequested; only Config.tsx's onCloseRequested listener confirms.) It also meant my test driver
    could not close the app from that screen. Suggested fix for a later phase: confirm the close in the main process when no user session is
    active.
  - The recovery path cannot tell the user if moving the damaged database fails for another reason (for example antivirus holding it): the
    login call would reject and the screen would stay on "Loading...". Rare; worth a friendly error in a later phase.
