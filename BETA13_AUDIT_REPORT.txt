1. EXECUTIVE SUMMARY
================================================================================
The three screenshot failures are not three bugs. They are one structural weakness seen from three angles:

   Clynx has FIVE separate, partly contradictory models of "what is this product", and the one place where
   a picture is actually written to a product (store.addProductImage) asks none of them.

The five models: (1) photoIdentity.ts + compIdentity.ts (Beta 12 text gate and comparable-sale model),
(2) productIdentity.ts (AI "attach / new / generic" judge), (3) identity/* foundation + safeguard (Phase 4 veto,
SHIPPED OFF by default), (4) store.isSimilarProductName / findMatchingProduct / productDuplicateKey (token
containment, used for ALL Database matching), (5) variantIdentity.ts / variantFamily.ts (variant research).
Pictures reach a product through 13 addProductImage call sites (section 4.1); the Beta 12 text gate guards four of them.

Headline findings (details in sections 3-9):

 ID-01 CRITICAL CONFIRMED  addProductImage is an unguarded choke point; 7 of 13 machine-driven call sites have no identity check.
 ID-02 CRITICAL CONFIRMED  Products and gallery moves are named from what the PICTURE looks like (vision subject,
                           gallery-audit "actualSubject", feedback re-file) while the listing/source title - which
                           contradicts it - is merely carried along as a label. This is exactly failure A:
                           a white Series X photo, whose own source title says "SERIES X", filed as "Series S".
 ID-03 HIGH     CONFIRMED  findMatchingProduct returns the FIRST fuzzy match in newest-first order, not the best one,
                           and token-containment makes a generic entry ("Xbox Series") absorb S and X, and makes games and
                           accessories ("Metroid Dread (Nintendo Switch)", "Nintendo Switch Dock") resolve to the console.
                           This is failure C's engine.
 ID-04 HIGH     CONFIRMED  The identity model has no concept of hardware configuration (disc drive vs All-Digital),
                           board design (MSI Gaming X Trio vs Ventus), region, carrier lock or SKU. Two visually different
                           MSI RTX 2070 SUPER cards are "exact" to each other; Series X All-Digital is "exact" to Series X
                           (and so is its valuation comp). This is failure B and the MSI screenshot.
 ID-05 HIGH     CONFIRMED  The Phase 4 identity safeguard (config.identitySafeguard.mode) defaults to "off": every
                           identityVeto(...) call site is a no-op in a default install.
 CV-01 CRITICAL CONFIRMED  Visual condition evidence NEVER reaches valuation. Vision flaws are off by default
                           (Config.researchCondition=false), and when on they are stored for a UI badge only.
 CV-02 HIGH     CONFIRMED  Condition is three buckets with flat multipliers (1 / 0.6 / 0.25) from a keyword list with
                           large gaps (scratch, dent, bent, hinge, corrosion, chip, drift, fungus, burn-in all = "none").
                           A cracked BACK glass and a cracked SCREEN cost the same 40%.
 LB-01 HIGH     CONFIRMED  "Folders" in the Library are not records. They are the string products.family split on ">" and
                           rebuilt in the renderer on every render. There is no folder table, no empty folder, no folder
                           id, and updateProductProfile OVERWRITES family+category on every research/refresh, so any
                           manual move would be silently reverted.
 LB-02 HIGH     CONFIRMED  Store.deleteProduct deletes the product row BEFORE its photos; on a schema with the declared
                           foreign key it throws "FOREIGN KEY constraint failed" for any product that has a photo.
                           (Fresh schema: confirmed. The owner's older database may differ: verify with library-db-audit.)
 UX-01 HIGH     CONFIRMED  There is no cancel, no tool-progress event, no elapsed time, no choice protocol; GlobalAssistantBar
                           and the Database product chat have no attachments (2 of 4 chats); ai:searchUpdate text is
                           appended into the assistant message and therefore into history.
 UX-02 MEDIUM   CONFIRMED  Attachments up to 4 x 8 MB (base64 ~ 43 MB) exceed the Clynx Cloud body limit (10 MiB);
                           the chat would fail with an HTTP error in shared mode, not degrade gracefully (arithmetic from
                           code; not exercised live).

What is already good and must be preserved (Beta 12 contract): the title gate (judgeCandidateByText) is correct
for every screenshot title - it rejects the Series X title for a Series S gallery (MODEL_LETTER), the Metroid / game-case
titles for a Switch gallery (MEDIA), and EVGA for MSI (TIER). The valuation path already has title-aware defenses
(modelLettersConflict, listingContradictsEntry, moreSpecificProductForTitle in store.ts). The failures are therefore
(a) gate not applied on most write paths, (b) things the gate cannot see (configuration, board design, region, lock),
(c) name resolution that picks the wrong entry before any gate runs, and (d) no way to see, quarantine or repair it.

Important baseline caveat (HYPOTHESIS, high likelihood): per the working record, Beta 12 had not been built,
registered or published when the screenshots were taken. The galleries in them were therefore most likely written by
Beta 11 or older, before the Beta 12 gate existed. That explains Nintendo Switch contamination WITHOUT a Beta 12 bug -
but ID-01/02/03/04 show that several of the same contaminations remain reachable in Beta 12 code, and no Beta 12 code
ever cleans an existing gallery (the gallery audit does not run below 3/10 photos, is off in Save-credits mode, and
decides by appearance). Section 13 gives the 2-minute check that settles which build the screenshots came from.

Recommended shape of Beta 13 (details in sections 10-12):
  1. ONE evidence-carrying identity model + ONE gate, and ONE writer for pictures (fileImage), enforced by a test that
     fails if anything else calls addProductImage.
  2. Never name a product from appearance. A picture may confirm or contradict; it may not create or rename.
     Conflicting evidence => "unresolved" => a quarantined image / "Needs review" item, never a silent move.
  3. Library becomes a real tree (folders table + products.folder_id), with auto-organization kept as the default and
     user placement as an override that research never overwrites. One typed operations service shared by UI and chat.
  4. Condition becomes structured evidence (defect class, location, severity, source, confidence) that reaches the
     gate as a defect-specific adjustment with an uncertainty range, with text+vision de-duplicated.
  5. Chat: one engine hook, one composer, a typed choice protocol, real status events, cancellation, short answers.
Estimated total: 28-42 engineer-days (section 11). Incremental OpenAI cost: well under $0.10/day at the owner's
scan volume (section 14; token assumptions flagged as such).

3.3 ID-02  CRITICAL  CONFIRMED (mechanism) / HYPOTHESIS (that it produced screenshot A)  Pictures name products
  Failure A: a white Series X filed as "Xbox Series S", with source title "MICROSOFT XBOX SERIES X - CONSOLE - 1TB - 1882 (G4P004519)".
  The source title is a Facebook/eBay-style listing title with no "eBay listing:" / "Stock photo" prefix, so it came through a scanner or a
  MOVE (which preserves the title), not through findReferencePhotos (which prefixes labels). Three code paths can put that exact pair together:
   (a) ensurePhotoGalleryAudit (index.ts ~1574-1591): vision reads the gallery by APPEARANCE ("a white console among black ones is obvious early" - the
       audit runs from 3 photos for any colour-named entry) and returns actualSubject; the code deletes the image from the source product,
       resolves findMatchingProduct(actualSubject) (first fuzzy match) or findColorVariant(), and calls store.addProductImage(target, imageData,
       image.sourceTitle). The source title travels with the photo; nothing compares it with the destination. A white Series X (Robot White)
       looks like "a white Xbox console", the Series S is the famous white Xbox, so "Xbox Series S (White)" is a plausible appearance-only answer.
       The prompt tells the model to treat "a different color of the same product" as a mismatch when the entry names a colour.
   (b) scrapeEngine ~2723-2736 + 2830-2910: visionSubjects = photoResult.identifiedProducts (free text from the picture). A subject with no
       existing entry and in specificSubjects goes to onNewProductFound(subject, image, listing.title): a NEW entry named by the picture, source
       title = the contradicting listing title. There is no title-versus-subject check on creation (identityVeto only runs for EXISTING entries,
       and is a no-op by default, ID-05). The Beta 12 listingMayFeedProduct guard sits on the existing-entry branch only.
   (c) resolveIdentityTarget -> action "create" -> createSpecificModel(action.name...): the NAME comes from the AI's specificName for the listing.
   Common root: the filing decision is derived from the picture/AI while the textual evidence that contradicts it is only stored as a label.
  Why the Beta 12 gate does not catch it: it exists only where the code calls listingMayFeedProduct / judgeCandidateByText.
  Policy violated: "never infer a model from appearance alone" (the brief's rule). The gallery audit, feedback re-file and vision subject
  creation all infer a model from appearance.
  Proposed correction: (1) a picture can CONFIRM or CONTRADICT an identity that text proposes; it can never create, rename or re-file one.
  (2) every move/creation is evaluated by the same gate with BOTH the picture verdict and the source-title verdict; text MISMATCH is final
  (as in withVision today); a picture-only proposal that disagrees with the title becomes status=conflict -> review queue.
  (3) the audit's "move" becomes "quarantine + suggest": the image leaves reference use immediately and a suggestion is queued; the user (or the
  chat, sections 7-8) applies it.
  Tests: fixture A (below) with a scripted vision answer "Xbox Series S (White)" on a Series X-titled image must end in quarantine, not in the S gallery.
  Regression risk: MEDIUM - the audit currently also fixes real misfiles automatically; quarantine keeps that benefit (the bad photo stops being
  used) without the risk.

3.4 ID-03  HIGH  CONFIRMED  Name resolution is first-match + token containment
  Evidence (store-probe section 1, products: Xbox Series X, Xbox Series S, Xbox Series S (Black), Xbox Series, Nintendo Switch, Nintendo Switch Lite):
     findMatchingProduct("Xbox Series S (White)")        -> "Xbox Series"      (exact "Xbox Series S" also matches; the generic one was newer)
     findMatchingProduct("Xbox Series X (White)")        -> "Xbox Series"
     findMatchingProduct("Halo Infinite (Xbox Series X)")-> "Xbox Series"
     findMatchingProduct("Xbox Series X Controller")     -> "Xbox Series"
     findMatchingProduct("Metroid Dread (Nintendo Switch)")/"Super Mario Odyssey Nintendo Switch"/"Nintendo Switch Dock"/"Joy-Con Pair"/"Game Case" -> "Nintendo Switch"
  Cause: store.findMatchingProduct (store.ts:1699) = exact name, else listProductIndex().find(isSimilarProductName) i.e. the FIRST row in
  ORDER BY created_at DESC. isSimilarProductName (store.ts:3113) accepts any name whose >=2 base tokens are all contained in the other, unless a
  variant word (pro/slim/max/plus/mini/lite/se/xl/oled/air), a storage size, a colour conflict or an edition term differs. "S", "X", "Dock",
  "Controller", a game's title are not in any of those lists. The same rule drives productDuplicateKey/mergeDuplicateProducts, listing->product
  linking (saveScored, store.ts:708), getEbayValueForProductName (first match again) and the vision-subject filing loop.
  Why it matters here: even a perfect gate downstream receives the WRONG TARGET. For failure C, a vision-named subject "Metroid Dread (Nintendo
  Switch)" resolves to the console entry, so game art lands in the console gallery whenever the path lacks a title (gallery moves, feedback re-file,
  free blank-product path) - and cleanFilingName (research.ts) lets such names through (store-probe section 2: only chargers/adapters are refused).
  Positive: valuation display is protected (store.ts:951-957: modelLettersConflict, listingContradictsEntry, moreSpecificProductForTitle).
  Proposed correction: best-match, not first-match: score every candidate by the identity model (section 10); require a unique best with margin, else
  "unresolved". Resolve platform-named software/accessories to their own kind (kindOfName) BEFORE console containment.
  Tests: the 14 subjects above must resolve as: S(White)->"Xbox Series S" (or its colour child), game/accessory subjects -> NOT the console.
  Regression risk: MEDIUM-HIGH (matching is used everywhere) - stage behind flag; keep isSimilarProductName for dedupe only.

3.5 ID-04  HIGH  CONFIRMED  The identity model cannot see hardware configuration, board design, region, lock, SKU
  Evidence (identity-probe B, E, F):
   - Failure B. "Xbox Series X 1TB" as the entry: titles "...1TB Carbon Black Console with disc drive" and "...1TB Robot White All-Digital Console" are BOTH
     text=match/exact, comp=exact. The only thing separating those two products in the current pairwise table is an accidental COLOR hit.
     "Xbox Series X" vs "Xbox Series X All-Digital no disc drive" = comp exact, editionConflict=false. The 2TB Galaxy Black Special Edition and the
     Halo Infinite Limited Edition ARE separated (EDITION / CAPACITY) - those cases work. variantIdentity classifies "...with disc drive" as bundle=true
     (the word "with").
   - MSI. "MSI GeForce RTX 2070 SUPER Gaming X Trio" vs "MSI GeForce RTX 2070 SUPER Ventus OC" = exact. Entry "MSI RTX 2070 SUPER" sees both titles as
     insufficient/compatible, and fileableWithoutPicture(compatible) = TRUE: in Save-credits mode both designs enter ONE gallery without any picture
     check; "MSI RTX 2070 Super Armor OC" is text=match/exact (no vision at all). distinguishingTokens() does see "gaming x trio" as `other` tokens but
     nothing consumes it for photos. Two visually different cards under one entry (the screenshot) is the designed outcome of today's rules.
   - Region / lock: "iPhone 13 128GB Unlocked" vs "...Verizon locked" = exact; "Nintendo Switch Japan Import" vs "US" = exact.
   - Accessory lexicon holes in the valuation model: "Nintendo Switch Carrying Case Pouch", "Console Stand", "Joy-Con Grip" = comp EXACT (the photo gate
     rejects them via accessorySignal, the comparable-sale model does not); "Skin Decal" rejected for the wrong reason (NOT_WORKING).
   - FALSE rejects (fail-closed, but starve galleries and comps): "Nintendo Switch Console Neon Blue Red Joy-Con 32GB HAC-001" => photo gate MISMATCH
     (accessorySignal sees "Joy-Con" as the head); "Nintendo Switch Console with Dock and Joy-Con Controllers HAC-001" => comp REJECTED (ACCESSORY);
     "Nintendo Switch HAC-001(-01) V2 battery" => REJECTED (ACCESSORY: "battery"). A genuine bundle/console set and a revised console are thrown away.
  Root cause: compIdentity attributes are model letter/number, generation, tier, capacity, colour, edition, accessory/lot/not-working, media. No attribute
  for drive/config, board design (AIB partner line), region, lock, SKU/MPN, nor a "headline noun" rule that separates "console WITH accessories" from
  "accessory FOR console".
  Proposed correction: extend the attribute set (section 10.2) with DRIVE (disc/all-digital), BOARD_DESIGN (GPU partner line), REGION, LOCK, SKU/MPN,
  each with a materiality class (value-defining vs cosmetic), and make the accessory/console decision use a headline-noun parse plus a bundle allow-list
  ("console with dock and Joy-Con controllers" is a console).  Photos use the STRICT set (any value-defining difference => not the same entry); valuation
  uses the same attributes but may down-weight cosmetic ones. Colour is value-defining only where tied to an edition or configuration (Galaxy Black
  Special Edition, Robot White All-Digital, limited-edition Halo) and cosmetic for products where colour does not move price.
  Tests: every pair above becomes an assertion table (section 13.3).  Regression risk: MEDIUM (valuation comps get stricter: fewer but cleaner comps -
  verify sample sizes in the AI Activity / comps counters before enforcing).

3.9 ID-08  MEDIUM  CONFIRMED  Evidence has no source or confidence anywhere it matters

  Each op: validates (exists, not deleted, permission, name rules), runs inside ONE `BEGIN IMMEDIATE` transaction, writes library_ops with its inverse,
  bumps products.updated_at (cloud LWW), emits one "library:changed" event, returns {ok, opId, summary, needsConfirmation?}.
  UI (Database.tsx) calls them through new IPC `library:op`; chat calls the SAME functions through a single chat tool `library_op` (typed args = the op union)
  plus read tools `library_list` / `library_find` (extend find_products). No second implementation of any rule; the chat tool is a thin adapter.
7.4 Safety rules
  - Soft delete only: products/images/folders get deleted_at; a Trash view restores for 30 days (configurable), purge is explicit. (Fixes LB-02 by
    construction; also makes undo of delete possible.) Hard delete stays internal for tests/clearAll.
  - Confirmation: ops are classified. Reversible & local (rename, move one product, reorder, set thumbnail) => execute + undo toast. Bulk or destructive
    (delete folder with contents, move > 10 items, replace image, merge) => needsConfirmation, rendered as a typed choice (section 8.3) in chat or a
    modal in UI; the op executes only with the confirm token returned by the first call (so a model cannot "confirm" for the user).
  - Integrity: parent must exist and not be deleted; moveFolder rejects cycles by walking ancestors (depth limit 8); name rules (trim, no "/" or ">" or
    control chars, <=80, no reserved "Needs review"/"Trash" at root); sibling name collisions are rejected with a typed error offering rename or merge-into.
  - Identity is untouched: moveProduct/renameProduct do not rewrite family, identity or comps; rename of a product is a DISPLAY name change that re-runs
    the identity resolver only as a suggestion (a rename that changes the model tokens shows "this changes what the product is" and needs confirmation);
    comps/valuation stay attached to product id, not to its folder.
  - Images: reassignImage and replaceImage run the identity gate and, if the gate disagrees, ask (never silently); user is authoritative, so the result
    is stored status='user' with the verdict recorded as a warning, not blocked.
  - Concurrency: the scanner/audits write the same tables between awaits in the single main process. Ops re-read and validate inside the transaction;
    background writers use the same fileImage/libraryOps functions (so they hit the same validation and see deleted_at). Optimistic check
    expectedUpdatedAt on bulk ops; a stale one returns {ok:false, reason:'changed'} with the current state.
  - Duplicates / collisions: images dedupe by content_hash per product (offer "already there"); two products with the same duplicate key are NOT merged
    by an op; the existing mergeDuplicateProducts is converted to propose-only (review queue).
  - Permissions: single-user local app; the relevant boundary is "chat may only call library_op, never raw SQL", ops validate ids against the open
    account's Database, and cloud accounts: ops go through the same Store so productSync's LWW applies unchanged. Image bytes accepted from the renderer
    are re-validated in main (type sniff, <=8 MB, re-encoded) - today setThumbnailFromImage trusts any string (4.5).
  - Audit log: library_ops (actor, op, args, inverse); chat-initiated ops are labelled; surfaced in AI Activity > Decisions and the Library "History".
  - Cloud sync: today only name/category/family etc. sync (006_products.sql); images, thumbnails, parent_product_id, variant evidence do not. Folders:
    Beta 13 ships LOCAL-ONLY (documented), because a cloud table + endpoints + conflict rules for a tree is its own project; the product's folder_id is
    not in user_products so another device shows the auto tree. Risk accepted/flagged in 15.4. upsertProductFromCloud must NOT clobber folder_id.
7.5 UI (keep what exists)

  products and folders, rename (F2 / inline), delete -> Trash, multi-select, per-product gallery edit mode (reorder by drag, set primary, replace, remove,

10. SHARED SYSTEMS AND DESIGN
================================================================================
10.1 Principles
  P1 Evidence over assertion: every identity or condition attribute is {value, source, confidence, evidenceRef, at}.
  P2 Text proposes, pictures confirm or contradict, users decide. Pictures never create/rename/re-file.
  P3 Conflict => unresolved => visible and reversible. Uncertainty is stored, not erased.
  P4 One writer, one gate, one operations service.
  P5 Additive, flagged, shadow-first, rollbackable.
  P6 Nothing is auto-deleted, auto-merged, auto-split or auto-renamed. Machines quarantine and suggest; people (or an explicit confirmed chat action) apply.
10.2 Unified product identity model  (new module identityModel.ts; compIdentity/photoIdentity/variantIdentity become adapters)
  Attributes (each {value, source: title|description|aspects|ocr|vision|user|web|db, confidence: high|medium|low, evidence}):
    manufacturer, categoryType (console|handheld|gpu|phone|laptop|accessory|game|...), family, model, generation, tier (slim|pro|oled|lite...),
    configuration { drive: disc|all-digital|na, storage, ram, boardDesign (AIB line), connectivity, ... }, edition (special|limited|bundle name),
    colorFinish, region (NTSC-U/J/EU, import), lock (carrier/iCloud/unlocked), sku/mpn/modelNumbers[], aliases[].
  Materiality classes: IDENTITY (manufacturer, categoryType, family, model, generation, tier) - different value => different product, always;
    VALUE (storage, drive, edition, boardDesign, region, lock, sku) - different => different entry for photos, comps compared with a stricter weight;
    COSMETIC (colorFinish) - different product ONLY when colour is tied to an edition/configuration (Galaxy Black SE, Robot White All-Digital,
    limited Halo) or the category table says so; otherwise a colour variant of the same entry (photo gallery scope "any colour"); LISTING-LEVEL
    (condition, accessories, bundle contents) - never part of product identity.
  Resolution output: {status: resolved|partial|unresolved|conflict, level: family|model|configuration|sku, attributes, missing[], conflicts[]}.
  Rules: (R1) conflicting hard attributes => conflict; (R2) vision-only attributes cap at confidence medium and cannot override a title model;
    (R3) an attribute absent from evidence is "unknown", not "matches"; (R4) generic entries ("Xbox Series") resolve at level family and CANNOT absorb a
    model-level listing - the listing attaches to the most specific existing entry or is unresolved; (R5) headline-noun parse decides
    console-with-extras vs accessory-for-console; (R6) never infer a model from appearance alone.
  Gate API: decideFiling(evidence, target, mode) => {outcome: file|quarantine|reject|review, reasons[], verdict} used by fileImage, libraryOps.reassignImage,
    the audit, importers. compIdentity.classifyComparable keeps its verdict names and gains the new attribute codes (DRIVE, BOARD_DESIGN, REGION, LOCK,
    SKU); the existing 75 tests must stay green (adapter, not rewrite).
10.3 Reference-image model: product_images gains status (trusted|unverified|quarantined|user|legacy), source_kind, source_url, verdict_json, content_hash,
  sort_order, is_primary, origin_product_id, deleted_at. Reference selection (4.2) uses status in (trusted,user,legacy-unsuspected). Review queue table
  review_items(id, kind image|product|merge, subject_id, reasons_json, evidence_json, state open|accepted|rejected|snoozed, created_at, resolved_at, resolved_by).
10.4 Condition evidence model: listing_condition(listing_id, defect_class, area, severity, source, confidence, photo_ref, quote, created_at) +
  adjustment summary on the gate facts (6.7). Shared with Watch/eBay engines through dealGate.
10.5 Shared services: identityModel.ts, identityGate.ts, fileImage.ts, libraryOps.ts, reviewQueue.ts, conditionEvidence.ts, chatEngine hook + ChatComposer +
  chatStatus reducer + ask_choice tool. All have flags (section 12) and AI Activity decision logging.

12. MIGRATIONS AND ROLLBACK
================================================================================
12.1 Additive DDL (ALTER TABLE ... ADD COLUMN, CREATE TABLE IF NOT EXISTS, via the existing constructor migration style + schema_flags for backfills)
  product_images: status TEXT DEFAULT 'legacy', source_kind TEXT, source_url TEXT, verdict_json TEXT, content_hash TEXT, sort_order INTEGER DEFAULT 0,
                  is_primary INTEGER DEFAULT 0, origin_product_id TEXT, deleted_at INTEGER
  products:       folder_id TEXT, name_locked INTEGER DEFAULT 0, deleted_at INTEGER, identity_json TEXT, identity_status TEXT, suggested_family TEXT,
                  thumbnail_image_id TEXT
  new tables:     library_folders, library_ops, review_items, listing_condition (section 7.2, 10.3, 10.4); indexes on (parent_id,name_key), product_images(product_id,status),
                  review_items(state), listing_condition(listing_id)
  schema_flags names: b13-image-backfill, b13-suspect-pass, b13-content-hash (lazy, in batches so a large DB never blocks startup).
12.2 Backfills (all non-destructive)
  - existing images: status 'legacy'; content_hash computed lazily in the background (aHash is already implemented).
  - suspect pass: judgeCandidateByText per titled image; mismatch => status 'needs_review' (excluded from reference selection, still shown with a badge); untitled
    images stay 'legacy' and are only judged when the owner runs the optional re-verification (cost 14.2).
  - products: identity_json filled lazily from the name by the extractor (source 'db', confidence low) - never overwrites a user value.
12.3 Risks
  - Making unverified images ineligible as references would starve vision (matchesClaim loses ground truth). Hence 'legacy' stays eligible except proven
    contradictions. Measure reference coverage before/after in shadow.
  - Soft-deleted rows reappear if the owner downgrades to Beta 12 (it does not filter deleted_at). Documented in release notes; a downgrade also ignores the new tables.
  - node:sqlite ALTER TABLE ADD COLUMN on a 500 MB DB is metadata-only (fast); the backfill is batched.
  - Cloud: no server migration. upsertProductFromCloud must not touch the new local columns (test).
12.4 Rollback
  - Per-feature flags (config.json beta13.*) can be set to "off" without a new build; "shadow" computes and logs only.
  - Pre-migration verified backup (dbBackups.createBackup); restore path exists (requestRestore -> prepareDatabase moves the current DB aside, never deletes).
  - Migrations are idempotent (CREATE IF NOT EXISTS, column-presence checks, schema_flags) - tested by opening a Beta 12 shaped database twice.
  - Nothing in Beta 13 deletes user data; quarantined/trashed items are restorable.

Prices from the repo (apiActivity.PRICE_PER_MILLION): gpt-5-mini input $0.25 / output $2.00 per million tokens. Image token counts are ASSUMPTIONS (about 765 tokens for a
1024 px image at auto detail; 85 at low detail) - the real figures should be read from AI Activity during the shadow phase; treat every number below as an estimate.
14.1 Per operation (incremental over today)
  Identity verification of one candidate image (1 image 765 + prompt 350 in, 120 out): about $0.0005. Today's binary check is ~60 output tokens: +$0.0001 (+20%) for structured evidence.
  A new product's photo fill (up to ~12 candidates, text-mismatches never reach vision): <= $0.006, same order as today.
  Condition: dedicated call (6 photos, 5.1k in, 300 out) about $0.0019 per listing; folded into the existing photo-analysis call about $0.0007 (extra 300 out + 250 prompt tokens).
  At the owner's scale (~300 evaluated listings/day, condition pass on the 5-10% that clear text+price) = $0.01-$0.06/day dedicated, $0.01-$0.02/day folded.
  Chat attachments: 1-4 downscaled photos = about 765-3,060 input tokens only on the turn they are sent: $0.0002-$0.0008. Brevity (900 -> ~350 max tokens) can only reduce output cost.
  Status events, choices, library ops, review queue, folders: no API cost.
14.2 One-time optional re-verification of existing galleries (user-triggered, non-destructive): batches of 8 images per call, about $0.0024 per 8 = $0.0003 per image;
  2,000 images about $0.60. library-db-audit prints the real image count.
14.3 Compute / memory / time
  - Identity model and gate: pure, microseconds. resolveProduct builds a token index once per products-changed event (N=1,500 trivial).
  - listProductImages(...) loads full base64 for every call (up to 20 x several hundred KB); add listProductImageMeta for lists and selection; only fetch bytes when drawing or sending.
  - products:list already ships every product's image_url data URI to the renderer (Beta 12 note: ~600 ms main-thread block for 266 listings elsewhere) - the tree service should return
    ids + small derived thumbs, not full-size data URIs. Out of scope to fix fully; do not make it worse.
  - fileImage adds a download + aHash already performed by the web path; the manual/scanner paths gain hashing (fast with sharp).
  - Defect-matched sold comps (6.4) add WatchCount Playwright tab time (several seconds per query): cache per (product, defect) for the existing MARKET_RECENT_MS window and budget with the
    existing 2/visit, 12/pass market allowances.
  - Vision work stays background / fire-and-forget as today, so the scan loop's critical path is unchanged.
14.4 Total: typical incremental < $0.10/day; one-time re-verification < $1; test corpus run about $0.03.
