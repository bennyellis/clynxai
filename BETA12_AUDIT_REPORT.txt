PRIORITY 1 / CHANGE 6 - WHY 300+ "INVESTIGATED" LISTINGS GAVE 2 DEALS
=====================================================================================================================================================

A. WHAT "INVESTIGATED" ACTUALLY MEANS (CONFIRMED) - three different numbers share the word
 1. Dashboard "Listings evaluated" = SELECT COUNT(*) FROM listings, all time (store.countListings, index.ts listings:count; Dashboard.tsx:207). That is every
    saved row, including listings that were NEVER OPENED (skipped from the search card by recordInstantSkip: wrong state, placeholder price, "unshippable" words,
    blacklist, over/under the item's price range, "not a Search For item", photo shows an ineligible category) and listings opened only to be skipped
    (too old, Facebook shipping/eBay mention, scam bot, seller risk). It does not count duplicates or no-price cards (never saved).
 2. The per-location line "Done at X (N listings evaluated)" counts only listings that were OPENED (result.counted).
 3. Activity > "Evaluated/sec" counts every call into evaluateListing, duplicates included.
 So "300 investigated" most likely means "300 rows saved since you started", not "300 listings fully evaluated". Also all-time, not per day.

B. THE FUNNEL, STAGE BY STAGE (CONFIRMED, scrapeEngine.ts / scorer.ts / research.ts / dealGate.ts / preAlert.ts)
 S0 Retrieval. Default mode (no Search For items, or general detection on) browses Facebook's generic "Today's picks" feed per location: ~18 cards per page
    (log evidence in the Beta 9 report: "found 18"). It is a recommendation feed across ALL categories, not a price-sorted or electronics view.
    A dedicated keyword search runs only when Search For items exist AND "Rotate search terms" is on, or there is exactly one item (see finding D4).
 S1 Silent drops (not saved, only visible in the pass accounting since Beta 9): already seen, no price.
 S2 Cheap filters, no page opened (saved as unresearched/rejected): OUT_OF_STATE, PLACEHOLDER_PRICE, UNSHIPPABLE (regex list: bikes, furniture, vehicles,
    "for rent", "lot for sale"...), BLACKLISTED, OVER_MAX_PRICE/UNDER_MIN_PRICE (the matched item's own range), NOT_FOCUSED, PHOTO_INELIGIBLE.
 S3 Detail page opened (1.2-3 s random pause + page load). A load failure is not saved and the listing is retried next pass (not seen yet).
 S4 Filters after opening: TOO_OLD (default 24 h), OFFICIAL_SHIPPING / MENTIONS_EBAY ("not a hidden local deal"), SCAM_BOT (masked phone number),
    SELLER_RISK (defaults: account at least 1 year old, profile photo required).
 S5 Text verdict (scoreListing):
      a) matches a Search For item -> deterministic price maths (free);
      b) title contains every word of a Database product that has an eBay value -> deterministic maths (free);
      c) anything else -> ONE text-only AI call (extractGeneralDeal) that estimates value from the model's memory; the prompt says "be conservative: the large
         majority should NOT be flagged"; needs confidence >= "medium" (default) to count.
 S6 Photo-look plan (research.planPhotoLook). Default "Save OpenAI credits" (lowAiMode) is ON: a listing the text read did not flag gets a photo look only if
    the read was unsure (low confidence / vague title) AND price >= $35 AND the visit budget (3) and pass budget (30) allow; otherwise it ends unresearched
    (LOOK_BUDGET / LOW_PRICE) or rejected (AI_ESTIMATE). A non-round price on an unknown title only moves the look behind others.
 S7 Photo analysis (2 background workers, priority queue, unbounded). If photos name a specific product ("photo-first find"): Database value -> maths; else a
    fresh WatchCount+eBay market look, allowance 2 per location visit, 12 per pass, price >= $35, otherwise NO_RESALE_NUMBERS (insufficient evidence).
 S8 Deal Quality Gate (dealGate.ts), run only for listings that are already isDeal / have counted extras / are Watch candidates (qualifyScoredListing call is
    guarded by that condition). Anything about to be pushed is first re-priced by a live market check (150 s limit).
    Evidence: strong >=5 sold comps, moderate >=3, weak otherwise or asking-price-only. A WEAK-evidence listing qualifies only with margin >= 2x the minimum.
 S9 Outcome: profitable_now / negotiation = a Deal; worth_a_look (kept, not pushed); pass.

C. THRESHOLDS (CONFIRMED, resaleMath.ts / profitGate.ts; defaults: keep 84% of the eBay price, minimum margin 20% OF PROCEEDS, negotiation reach 15%)
 The maths is internally consistent and matches its comments. Margin is measured against what you KEEP, not against what you pay, so:
     Deal now ............ price + shipping <= 0.672 x eBay value        (20% of proceeds = 25% return on cost)
     Negotiation deal .... asking price   <= 0.79 x eBay value           (needs <= 15% off)
     Weak evidence ....... price + shipping <= 0.504 x eBay value        (margin >= 40% of proceeds)
     Minor condition word  = value x 0.6  -> 0.40 / 0.47 of the nominal value;   major condition word = value x 0.25 -> 0.17 / 0.20
 Example, a console worth $400 on eBay: deal at <= $268 (negotiate up to $316); with "as is" anywhere in the text <= $161 ($190); with little sold history <= $201.
 Verdict: not a calculation bug. It is a strict policy; together with the weak-evidence rule it makes qualifying deals rare by design. Whether Marketplace
 prices in your categories ever sit below ~67-79% of eBay value is a MARKET question I cannot answer without your data (HYPOTHESIS that this is a large part of it).

D. CONFIRMED DEFECTS AND STRUCTURAL LOSSES (ranked by likely impact on the missed-deal count)
 D1  Unknown products are judged on the AI's memory and never validated when it says "no" (CONFIRMED).
     A listing for a product the Database has no numbers for, whose text read says "not a deal", ends rejected/AI_ESTIMATE ("Clynx's own estimate, not market
     numbers"). The market check only runs for listings already flagged as deals. In default Save-credits mode no photo look happens unless the read was unsure, and
     then only inside the 3-per-visit / 30-per-pass budget. A model told to be conservative, answering from memory, with no real prices, is the weakest link in the
     chain, and its "no" is final. (Not "ignored because not in the Database": the photo-first and AI-flag paths do exist - but they are throttled, see D9.)
 D2  Condition words are applied with no negation (CONFIRMED, probe of the real patterns):
        "works perfectly, no damage, not broken"      -> minor (value x 0.6)
        "Sold as is, works great"                      -> minor
        "Nothing is cracked or damaged"                -> minor
        "screen not cracked"                           -> minor
        "no dead pixels, no cracks"                    -> MAJOR (value x 0.25)
        "dead mint condition" / "no power issues"      -> MAJOR
     The text scanned is title + the whole page text ("may be noisy, includes unrelated UI text" per the scorer's own comment), so even unrelated words on the page
     can trip it (HYPOTHESIS for the page-text part). This lowers the value used by the Search For maths, the Database-known maths and photo-first finds, so a
     listing that is a real deal on paper is recorded as confirmed_unprofitable. This is a CONFIRMED false-negative source; its frequency in your data is unknown
     (the benchmark below counts it).
 D3  Dedupe by listing id only, forever (CONFIRMED, store.hasSeenCached, evaluateListing first lines). A listing seen once is never evaluated again:
       - a seller dropping the price is never noticed;
       - a listing first seen when the look budget was spent, the AI was unavailable, the Database had no numbers yet, or Clynx was closed (INTERRUPTED) is never
         revisited after the Database learns the product;
       - a worth_a_look listing is never re-checked.
 D4  Search For + general discovery interact badly in the DEFAULT multi-item mode (CONFIRMED, scrapeEngine.ts ~3299-3560). With 2+ Search For items and "Rotate
     search terms" off (default false), generalSearchMode is true: NO dedicated Facebook search runs, and the general feed is filtered down to titles relevant to
     the Search For list EVEN WHEN "general deal detection" is ON. So general discovery of unrelated products silently does nothing in that mode and the yield is
     "Search-For-relevant cards that happen to be in a ~18-card generic feed". Also: Config.load resets searchItems to [] and generalDeal.enabled to its default at
     every launch (config.ts ~428-430), so the setup is rebuilt each session.
 D5  A late market-check answer never re-qualifies the listing that asked (CONFIRMED: marketCheckSettle.ts only files the product; no code re-gates a listing).
     The listing stays worth_a_look / AI_UNVERIFIED and no alert is ever sent for it. Beta 9 fixed the lost product and the wrong-location attribution, not this.
 D6  Seller risk defaults reject after the page is opened (CONFIRMED defaults: min account age 1 year, profile photo required) - a new or photo-less seller's
     genuine bargain becomes SELLER_RISK. Frequency unknown (HYPOTHESIS that it matters).
 D7  Scoring failure leaves an opened listing unsaved (CONFIRMED, scrapeEngine ~2090-2093): counted as "opened", no row, no reason; it is retried next pass, so not lost,
     but it is an accounting gap.
 D8  Counting is not comparable (see A). Also PHOTOS_QUEUED listings already count as evaluated while their verdict is pending.
 D9  Budgets throttle the "profitable unknown product" paths (CONFIRMED constants): 3 speculative photo looks / visit, 30 / pass, 2 market looks / visit, 12 / pass,
     $35 floor for both. At ~18 cards per location most unknown listings can never get either.
 D10 One structural fact, not a defect: the queue is unbounded and ordered by priority, so late = slow, not dropped; closing the app marks waiting ones INTERRUPTED
     (insufficient evidence, not a verdict).

E. QUESTIONS ASKED, DIRECT ANSWERS
 - What is "investigated"? A saved listing row (see A). Many were never opened.
 - How many reach complete evaluation? Cannot be stated without your database. A listing is "completely" evaluated only if it is opened, passes S4, gets a verdict
   AND (S6-S8) either a photo look or a Database/Search For price. The benchmark prints this split.
 - Where rejected/skipped/deferred/lost? Table in B. "Lost" candidates: D3 (never revisited), D5 (late answer), D6.
 - Is failed research treated as unprofitable? CONFIRMED NO for the main failures: AI/text judge unavailable (TEXT_JUDGE_UNAVAILABLE), photo failure
   (PHOTO_ANALYSIS_FAILED), photo background crash (RESEARCH_FAILED), no AI (AI_UNAVAILABLE), market check failure/timeout -> worth_a_look / insufficient_evidence. Remaining
   risk (HYPOTHESIS): when the market check fails the gate falls back to the Database's existing value; if that value is old or thin the gate can still return
   "pass" -> confirmed_unprofitable on stale numbers.
 - Do queues/timeouts/late results cause misses? Yes, via D5 and D3; the queue itself does not drop work.
 - Do general discovery and Search For settings interact incorrectly? Yes, D4 (and the Beta 9 add-switches-general-off bug is already fixed).
 - Do identity/comp errors produce false negatives? Yes in two ways: D2 (value cut by condition text) and, for Database-known products, listingContradictsEntry /
   compMatchesSpecs can make a title decline a Database value (by design, protects against wrong-product pricing; frequency unknown). The comp-identity audit
   (COMPARABLE_IDENTITY_REPORT.txt) also found a RECALL gap: "Xbox Series X 2TB Galaxy Black Special Edition Console" is rejected against an entry named "... Galaxy Black
   Edition" (EDITION_PHRASE), reproduced again this audit.
 - Profitable unknown products ignored? Throttled, not ignored (D1, D9).
 - Photos used appropriately for vague listings? In design yes (speculative looks), but budget-capped (D9) and OFF for listings the text AI confidently dismissed (D1).
 - Thresholds calculated correctly? Yes (C). They are strict.
 - Non-round-price scam filter: PRESERVE. Current behavior (CONFIRMED, scrapeEngine.ts:1559 comment + planLook): a non-round price is NOT a skip any more (it caused real
   misses); it only moves a speculative photo look to the back of the queue when the title names nothing known. The scam rules that do skip are the masked-phone scam-bot
   detector and the placeholder-price filter. Nothing in the recommendations below touches either.

H. RECOMMENDED IMPLEMENTATION (Change 6), smallest effective set, in order
 1. Condition wording: negation-aware detection (no/not/without/never/nothing within a few words; "as is" only when it is not "as is, works"), and scan the title + the
    description text only (not the whole noisy page). Pure function + tests. Complexity S.
 2. Re-qualify on late/improved evidence: when a market check files late, or the Database gains a value for a product, re-run the gate for listings that are
    worth_a_look/insufficient_evidence in the last N hours (cheap, no Marketplace visit); alert once if it now qualifies (reuse isListingNotified). Complexity M.
 3. Revisit rather than "seen forever": keep the dedupe, but re-evaluate an already-seen listing when its PRICE changed (card price differs from the saved price) or
    it ended in an evidence-gap state and the evidence now exists. Needs saved price compare in evaluateListing. Complexity M.
 4. Validate "no" for unknown products cheaply: for a text-dismissed listing above a price floor, let the Database/WatchCount path (not photos) price the title once per
    product name (cached per product, not per listing), instead of the AI's memory. Complexity M-L; affects AI/network cost - needs your decision on budget.
 5. Fix D4: in multi-item mode with general detection ON, do not relevance-filter the feed (or run a real per-item search with rotation default ON). Must not add Facebook
    queries beyond today's pacing - this is a decision for you. Complexity S (filter) / M (search).
 6. Clear counters: show opened / skipped-before-opening / duplicates separately in Dashboard and Activity. Complexity S.
 7. Persist (or restore) Search For and general toggle across restarts, or make the reset visible. Complexity S.
 Risks: any change that lets more listings reach the market check raises OpenAI/WatchCount use and Marketplace page loads (pacing must stay); changing condition handling
 changes which listings alert (guard with tests and a flag); re-qualification must never alert twice.
 Regression tests: negation table (the probe rows above + real damage rows must stay minor/major); late-check re-gate alerts exactly once; price-drop re-evaluation;
 generalSearchMode keeps/does not keep unrelated listings per the chosen setting; counters add up (passAccount); the non-round-price and scam-bot cases unchanged;
 failed research never becomes confirmed_unprofitable.
 Complexity overall: L (items 1,5,6,7 are small; 2-4 carry the weight).

PRIORITY 2 / CHANGE 3 - REFERENCE-PHOTO CONTAMINATION (Guardians of the Galaxy game filed under Xbox Series X Galaxy Black Edition)
=====================================================================================================================================================
1. Current implementation. Candidates: webResearch.gatherReferenceCandidates (Wikipedia exact-title image; Bing "name" and "name product photo"; the chat tool adds user
   link queries first and "name used for sale"; eBay Browse results for the name when credentials exist; cap 44). Verification: webResearch.findReferencePhotos ->
   vision.verifyThumbnailCandidate(..., "reference"): one vision call per image at minimal reasoning, which sees ONLY the product name text. Errors fail closed here.
   Save: referencePhotos.topUpReferencePhotos / store.addProductImage (no dedupe across products, no verification of its own, prunes oldest past 20).
2. Confirmed defects (CONFIRMED by code and probes; the exact path that stored YOUR image is a HYPOTHESIS until its sourceTitle is read - "Stock photo -", "Image search -",
   "Real-world photo -" or "eBay listing photo -" identifies the source):
   a) The "reference" prompt (vision.ts:1092) ACCEPTS "packaging/box art or cover art for it" and does not reject games/software/discs; its reject list names accessories,
      parts, cases, logos, screenshots. A cover reading "Guardians of the Galaxy - Xbox Series X" is easy to accept against the name "Xbox Series X Galaxy Black Edition"
      (HYPOTHESIS on the model; the prompt gap is confirmed). The other prompts (matchesReferenceProduct, comp photo check) do say "not a game, accessory".
   b) In full-AI mode eBay candidates are added with NO title filter (webResearch ~1002-1008); the free path filters, the paid path does not.
   c) titleLooksLikeProduct (free path and low-AI comp judge) is a bag-of-words test: "Marvel's Guardians of the Galaxy - Xbox Series X Game Disc Black Case" is accepted for
      "Xbox Series X Galaxy Black Edition" (probe). ACCESSORY_WORDS has no game/disc/software words.
   d) Fail-open: thumbnail checks accept on a verifier error (webResearch:444), low-AI mode uses NO vision at all for reference photos (findFreeReferencePhotos), and
      researchBlankProduct's free path stores Wikipedia/eBay images unchecked.
   e) Eight of twelve code paths that call addProductImage have no vision check (scanner/Search-For listing photos filed under the matched entry, mark-interested,
      new-entry creation, manual actions are by design the user's or the listing's own photo; but listing photos are filed on a title match that games also satisfy).
   f) The gallery audit (ensurePhotoGalleryAudit) only runs from 3 or 10 photos up, uses consensus, skips in low-AI mode - a contaminated majority is not caught.
3. Root causes (ranked): permissive context-free verifier prompt; no product-type (console vs game) vocabulary anywhere in the identity text checks; unverified paths;
   unfiltered eBay source; user-supplied search phrases ranked first.
4. Similar weakness in comparable-sale valuation (CONFIRMED by probe of classifyComparable for "Xbox Series X Galaxy Black Edition"):
     "Guardians of the Galaxy (Xbox Series X) Brand New Sealed" -> compatible (usable);  "... Xbox Series X|S Black Edition game" -> exact;
     "Marvel's Guardians of the Galaxy ... Game Disc Black Case" -> exact;  Series S Galaxy Black, controllers, skins, for-parts -> rejected;
     real "Xbox Series X 2TB Galaxy Black Special Edition Console" -> rejected (EDITION_PHRASE: recall gap).
   Backstops that exist: the AI judge (judgeSameProduct) which names games, the comp photo check, category restriction when the family says Consoles, the eBay product
   filter's category taxonomy. They are weaker in low-AI mode (same title test) and when the gallery itself is contaminated (the photo check uses the entry's own photos).
5. Recommended implementation (M, with a path-unification part that is L):
   - Add "reject video games, software, discs, game cover art and merchandise that merely names the platform or shares a word, unless the product itself is that game" to the
     reference and product prompts, and pass the product's family/category (console vs game) into the prompt.
   - One shared looksLikeMediaOrAccessory(title) guard (game, disc, steelbook, DLC, "(Xbox Series X)" platform badge, Funko/LEGO...) used by titleLooksLikeProduct,
     compIdentity ACCESSORY_WORDS and the Search For variant filter (Change 4) - one vocabulary, three consumers.
   - Run titleLooksLikeProduct on eBay candidates in the paid path too; fix the label mismatch ("eBay listing photo -" vs the "eBay listing:" prefix used for the cap).
   - Reference gallery photos must be vision-verified or tagged unverified; thumbnails may stay lenient. Free-path images go to the thumbnail only.
   - Audit each newly saved photo against the gallery at save time; do not wait for 10 photos.
   - Fix the EDITION_PHRASE recall gap (accept "Special/Limited Edition" when the reference already says "Galaxy ... Edition").
   - Migration: DO NOT auto-delete existing photos. Offer a one-time "review suspect photos" list (reuse the gallery audit) so the user decides.
6. Risks: stricter prompts may reject real box art for products that ARE games (gate the clause on category); fail-closed thumbnails leave more entries blank during an
   outage (blank sweep retries); media-word guards can hit "console with game" bundles (the existing bundle exemption must stay).
7. Regression tests: compIdentity cases above (games rejected for both "Xbox Series X Galaxy Black Edition" and "Xbox Series X"; real Galaxy console titles still accepted);
   referenceCandidates (a game title from mocked eBay is not added); a vision prompt contract test pinning the new clause; verifier-error policy per photo kind;
   a test that every addProductImage caller is verified or tagged.
   Complexity: M (prompts + guard), L with path unification.
   OPEN QUESTION that changes the fix: read that image's stored sourceTitle (Product page > photo details) - it tells us which path let it through.

PRIORITY 3 / CHANGE 4 - SEARCH FOR VARIANT MATCHING (optional, no extra Facebook searches)
=====================================================================================================================================================
1. Current implementation. SearchItem (types.ts:18-60); matching in scorer.ts: matchSearchItem / isRelevantToSearchItems / findGreenFlagCandidate = every word of a keyword phrase
   must appear in the title (any order, word boundaries), minus accessory-only phrases, minus six "variant qualifier" words the item did not ask for (pro, max, plus,
   mini, lite, se, xl, oled, air), minus model-letter conflicts. The Facebook query is getSearchQuery(item) = item.item, fixed (scorer.ts:35; scrapeEngine 3313/3417/3676).
   Price bounds go into the URL and are re-checked per listing (scrapeEngine 1748-1771). Search For items are session-only (reset every launch); Recent searches persist.
2. Confirmed behavior (probe). A plain "Xbox Series X" item ALREADY matches: 2TB Galaxy Black Special Edition console, 1TB Black, Digital, Halo Limited Edition... but also the
   controller, a cooling stand, a skin and games that name the platform ("Guardians of the Galaxy (Xbox Series X)"). It correctly rejects Series S and Xbox One X. The reverse
   (a specific item such as "Xbox Series X Galaxy Black Edition") does not match plain "Xbox Series X 1TB". So today there is no "family" mode: it is "contains all my
   words". Only downstream photo checks stop games - skipped when photo analysis is off or in Save-credits mode (a listing then keeps the base model's price).
3. Root cause of the need: the item has one string; a family and a specific variant cannot both be expressed, and the permissive matcher has no product-type guard.
4. Recommended implementation (M-L):
   - New optional SearchItem field acceptVariants (default false = byte-identical to today) plus familyTerms resolved at add time (linked Database product's parent, else
     findParentCandidate, else the user's own words). Thread it like includeBroken (Dashboard add flow and checkbox, preload, search:addProducts, add_search_item chat tool,
     RecentSearch + its dedupe key sameSearch).
   - The Facebook keyword stays item.item: no new queries. The decision is made AFTER retrieval in one helper used by matchSearchItem and isRelevantToSearchItems:
     accept when all family words are present, no unrequested qualifier/model-letter conflict, classifyComparable(family, title) has no hard reasons (ignore EDITION, CAPACITY,
     COLOR - those are what a variant adds), the shared media/accessory guard passes, and the extra tokens are capacity/color/edition/region or a themed word next to the
     family phrase. Probe of a first version: accepts 2TB Galaxy Black, 1TB Black, Digital, Halo Limited; rejects Series S, Xbox One X, controller, stand, game disc, Call of Duty,
     for-parts, storage cards; STILL accepts "Guardians of the Galaxy (Xbox Series X) Brand New Sealed" with token rules alone - so add the structural rule (family phrase inside
     parentheses/after a dash, or preceded by other title words + "of/the", means platform badge) and the shared media guard.
   - Valuation: a variant-only match must NOT use the item's typicalResaleUsd (a Digital or Galaxy model against the base price makes false deals or false misses): use the
     variant's own Database entry if present (moreSpecificProductForTitle) else the "no reference price" path, which defers to evidence.
5. Risks: price range min/max applies to the whole item (a variant range excludes base listings and vice-versa; say so in the UI and in skip reasons); Galaxy-type word collisions
   remain heuristic (keep the photo claim check as last gate); Watches share the SearchItem shape (leave undefined); eBay Search For uses the same filter; no migration needed
   (searchItems is cleared each launch; old recent searches default to false).
6. Regression tests (new searchVariants.test.ts): flag off identical to today; accept/reject tables above; getSearchQuery unchanged; price floor/ceiling still skip variants;
   variant-only match never uses typicalResaleUsd; recentSearches dedupe with/without the flag.
7. Complexity: M (field + UI + plumbing), M-L (matcher + valuation guard + tests). Depends on Change 3's shared media guard.

PRIORITY 4 - INTERFACE AND NAVIGATION (CHANGES 1, 2, 5)
=====================================================================================================================================================
Shared facts (CONFIRMED, src/renderer/src). Routing is plain state: App.tsx screen via useState (line ~195); Sidebar onClick -> handleSelectScreen (App.tsx ~311) which only
blocks leaving a dirty Config. All six screens stay MOUNTED and are hidden with display:none (FreezeWhenHidden/ScreenActive in lib/screenActive.tsx), so Database keeps its own
state across sidebar switches. There are three separate chat UIs (DiscoveryTab, Activity, GlobalAssistantBar) and no shared message-list component. No renderer unit tests
exist (no jsdom/testing library): logic must be extracted to pure functions in lib/ (like lib/scannerState.ts) to be testable.

CHANGE 1 - Discovery chat flows downward; conversations separate from scanner activity
 1. Current: DiscoveryTab.tsx. User/assistant messages are a module-level array thread (line ~39). Scanner/automation is a different type: DiscoveryEntry from main/discovery.ts
    (in-memory DiscoveryFeed, one entry per product with thoughts, pushed on IPC discovery:entry). They are merged only in the renderer: stream memo (lines ~228-238) builds a
    union of {product entry} and {chat user+reply} and sorts NEWEST FIRST (b.ts - a.ts); the static greeting bubble renders last. Scroll container data-testid="take-scroll".
 2. Confirmed defects: newest-at-top (opposite of chat convention and of Activity); conversation and product cards interleave by timestamp so a busy scan buries the Q&A;
    no stick-to-bottom, only scrollTo(top) after sending; chat history is lost on restart (module state, nothing stored); Q/A pairing assumes strict alternation; switching Database
