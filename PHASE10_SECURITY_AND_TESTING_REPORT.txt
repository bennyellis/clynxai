2. THREAT-BY-THREAT REVIEW
--------------------------
Authentication and sessions
  - Website sign-in uses a random 256-bit session secret in an HttpOnly, SameSite=Lax cookie (prefix __Host- and Secure when the site address is https). Only a SHA-256 of the secret is stored; the browser never sees the stored value.  [IMPLEMENTED, TESTED]
  - Sessions expire (default 14 days), can be listed and revoked by the owner of the account, are revoked on password reset (all) and password change (all others), and die immediately when an account is disabled.  [TESTED]
  - Passwords: Argon2id, length-capped. Login is throttled per IP+email (8 failures / 15 min) and does not reveal whether an email exists. Registration is throttled per IP.  [TESTED]
  - Desktop sign-in keeps using short-lived bearer tokens (15 min) with rotating refresh tokens (30 days), hashed at rest, reuse-detecting, and now rotated inside a transaction with a per-user lock (a race found and fixed during Phase 10).  [TESTED]
  - NEW: a desktop sign-in is now tied to its device. Revoking a device on the website ends that desktop's sign-in at its next refresh (at most ~15 minutes) even if the device was removed before its first refresh. Found by the real-server Electron test: before this fix the device row was deleted but the desktop's refresh token stayed valid.  [TESTED, REAL]
CSRF
  - Every state-changing request made with the cookie must carry the per-session CSRF token (X-CSRF-Token) and a same-origin Origin header; bearer-token clients (the desktop) are not cookie-based and so not exposed to CSRF. Enforced inside the one shared authentication gate so every existing endpoint accepts either, with no endpoint able to forget it.  [TESTED: missing token, wrong token, foreign Origin all refused]
XSS / injection / content
  - Strict Content-Security-Policy on every page: scripts, styles, fonts, images and connections only from the site itself (inline styles only as attributes); frame-ancestors none; object-src none; base-uri none. No third-party scripts, no analytics, no ads, no external fonts (fonts are bundled).  [TESTED: header asserted in the image smoke test and static tests]
  - React escapes all text; the support form and bug-report fields are validated and length-limited; admin pages show customer text as plain text. SQL uses parameters throughout. Release file names are generated by the server (user-supplied names are not used as paths).
Rate limits and abuse
  - Limits per IP/account: login, registration, forgot password (20/h per IP, 3/h per email), reset (20/h), resend verification (3/h), email change (5/h), account deletion (5/15 min), support requests, AI requests, concurrency per user, eBay calls. State is in Redis; if Redis is unavailable the AI spend reservation falls back to per-instance memory (documented limitation).
  - Abuse detection on the company-managed APIs: unusual request volume or error patterns flag the account and can temporarily block it; admins can clear flags; the Owner has an emergency switch that stops every paid call at once.  [TESTED]
Authorization (RBAC) - enforced on the server for every request
  - Roles: user, admin, owner. Admin pages/APIs require admin or owner AND a cookie session (a bearer token from a desktop cannot reach the console). Credentials, spending limits and the Owner-only switches require Owner.  [TESTED: ordinary users and admins get 403 on the Owner-only routes; users cannot read other users' data, devices, sessions or subscriptions]
  - Owner role: cannot be set through registration, profile edits, any API, an email comparison or a frontend flag. It is granted only by a server-side command (npm run owner -- begin / complete) using a one-time code (hashed at rest, 15 minutes, single use). A database trigger refuses any change to the owner role outside that procedure and a unique index allows only one Owner. Granting Owner signs that account out everywhere. The Owner account cannot be deleted from the website; admins cannot disable the Owner; only the Owner can disable an admin.  [TESTED: 17 tests including "ordinary users cannot grant themselves Owner"]
  - Admin is NOT Owner: admins never receive free subscriptions or credential access.
  - Owner has full feature access and no payment requirement ("Owner - Full Access" is shown in the account dashboard; billing actions are refused for that account). Infrastructure safety limits (rate limits, concurrency, global budget, emergency switch) still apply to the Owner.  [TESTED]
Secrets management
  - No secret is in the repository or in any client bundle (scanned: the built website contains no key-shaped strings; the earlier installer-contents test confirms the desktop installer carries no source, keys or data). .env.preview (generated secrets) is git-ignored; examples contain placeholders only.
  - Company OpenAI/eBay credentials: stored only in the database, AES-256-GCM encrypted with CREDENTIALS_ENCRYPTION_KEY (key id recorded; optional previous key for rotation). The plaintext exists only in server memory for the duration of a call. After saving, the console shows only a masked hint (for example "sk-...ab12"), the last verification time and status; there is no endpoint that returns the secret. Replace / rotate / revoke / verify are Owner-only and audited (the audit log never contains the secret). A revoked credential stays revoked (the environment fallback is used only on a server that never had a saved credential).  [TESTED: isolation (users/admins cannot read), rotation, revocation, wrong-key and damaged-ciphertext handling, no leakage in responses or logs]
  - If CREDENTIALS_ENCRYPTION_KEY is lost, stored credentials become unreadable (the console says "needs re-entering"); nothing else is lost. Back the key up separately from database backups.
  - Stripe keys and webhook secret are environment variables only.
Customer data: privacy, export, deletion
  - Collected: email, optional display name, password hash, subscription status, device list, support messages the person sends, usage counters (AI/eBay request counts and ESTIMATED cost per customer - no prompts or responses are stored). Facebook sessions and listing photos stay on the customer's computer.
  - Download analytics: one counter per release per day. No IP address, browser string, or account is stored.
  - Cookies: one essential sign-in cookie. No advertising or analytics cookies. The cookie policy page says exactly this.
  - Export: /web/export returns the person's account data as a file. Deletion: from the website with password + typed confirmation; cancels any live subscription FIRST (if cancelling fails the account is NOT deleted); removes all rows by cascade. The Owner is refused (the role must be removed with the server tool first).  [TESTED]
  - The five legal pages (Privacy, Terms, Subscription/cancellation, Refunds, Cookies) are DRAFTS, marked as drafts on the pages, and are not legal advice. Refund policy is explicitly undecided. They need a lawyer before launch.
Billing safety
  - Provider interface; checkout/portal return URLs come from server configuration (never from the request); webhooks are signature-verified, idempotent (event id is the key) and order-safe; a subscription's state is only changed by verified events or by the server's own API calls to the provider. BILLING_FAKE (the local stand-in) is refused when NODE_ENV=production.  [TESTED SIMULATED]
  - Owner has no subscription; existing customer subscriptions are never modified by Phase 10 code or migrations.
Release management
  - Installers are uploaded by an admin, the SERVER computes SHA-256 and size, and publishing needs: approve -> publish with the version typed to confirm -> the checksum re-verified against the stored file. Only published releases are visible to the public; drafts/approved/withdrawn are invisible. Promotion beta->stable creates a draft that must be separately approved and published. The installer is unsigned until you obtain a code-signing certificate (SmartScreen warns); signed-update delivery is "readiness" only (the verifier core exists, delivery is not built).  [TESTED]
  - Nothing was published. The preview database contains one DRAFT entry registered from the real beta installer, not approved, not published, on a local preview server only.
Desktop
  - Local beta mode is unchanged (regression suite t16 passes): no account, no cloud requests, no subscription enforcement for beta testers.
  - Signing in from the desktop never deletes or overwrites local beta data: optional "copy my local data" copies the Database, settings and Facebook profile into the new account's folder; the local-beta folder is left byte-for-byte unchanged (hash-verified in the real-app test); leaving the account returns to local mode with the original data.
  - Offline: if the server is unreachable the app opens with the account's local data, says "You're working offline", does not discard the sign-in, and reconnects by itself when the server returns (tested by stopping and restarting a real server under a real app).
  - Cloud mode needs no OpenAI or eBay key. Keys already saved by a beta tester are kept exactly as they were until the person chooses "Use Clynx's shared AI and eBay" (keys still kept) or "Delete my saved keys" (explicit confirmation).
  - When Clynx's shared service says no (daily plan allowance, per-customer budget, company budget, emergency switch, temporary block) the app shows a plain message and pauses AI calls for a few minutes instead of failing repeatedly.


3. DESKTOP API-KEY STORAGE: EVALUATION AND MIGRATION
----------------------------------------------------
Finding: the beta stores a tester's own OpenAI key (and optional eBay App ID / Cert ID) as PLAIN TEXT in .env in the Clynx data folder. Anyone or anything that can read that folder as the same Windows user (other programs, a backup tool, a support zip) can read it. The support report already strips keys; the installer ships none.
Risk assessment: moderate for the tester (the key is billable), low for Clynx (keys are the tester's own, not Clynx's).
What was built (opt-in only; nothing changes for anyone who does not turn it on):
  - Config > Account > "Protect my saved keys". When turned on: (1) a full copy of .env is saved next to it (.env.backup-<time>); (2) only the three key lines are encrypted with the operating-system key store (Windows DPAPI via Electron safeStorage; tied to this Windows account); (3) each key is decrypted again and compared before the file is replaced - any mismatch or unavailable key store aborts with nothing changed; (4) keys saved later stay protected. Turning it off restores plain text the same way. The leftover backup copies (which hold the old plain keys) are listed and can be deleted on request with one button.
  - A protected file copied to another computer/account reads as "no key saved" (enter it again); it never crashes the app. A key that cannot be decrypted is never silently deleted.
  - Tested: 15 unit tests (round trip, quotes, other lines untouched, double-protect, refusal when the key store is unavailable or the copy does not read back, unreadable keys) and the real app (protect -> key file contains no key -> restart -> key still works with the server down -> turn off -> plain again -> delete copies).
Recommendation: leave it OFF by default for existing testers (changing their files unasked is not acceptable), but ship it, and make cloud mode (no keys at all) the normal path: once customers use Clynx's shared service they have no local key to protect.


4. COST CONTROLS (company-managed APIs)
---------------------------------------
Implemented and tested with stubs: per-customer and per-plan daily USD limits, global daily and monthly USD limits, spend RESERVED atomically before each call (6 parallel requests cannot all slip under the limit - a bug found and fixed in testing), concurrency limits, eBay call caps, abuse blocks, emergency stop, and cost attributed per customer. IMPORTANT: the cost numbers are ESTIMATES from a built-in price table (override with AI_PRICES_JSON). The provider's invoice is the truth. Set the limits in the console BEFORE opening to customers. Defaults are conservative but are not a substitute for a billing alert on the OpenAI account itself.


5. KNOWN GAPS AND RISKS (honest list)
-------------------------------------
 1. Real Stripe, real email, real OpenAI, real eBay were never contacted (section 1). First live contact will teach us things; plan a test-mode rehearsal in staging.
 2. The legal pages are drafts; the refund policy and plan prices are undecided (the Pricing page shows a placeholder, no invented prices).
 3. FONT LICENSE (desktop app): the app's Made Tommy Soft font files are marked "free for personal use only". Commercial distribution needs a license or a replacement font. The website uses Nunito (open license) and is not affected.
 4. Facebook's terms restrict automated access; get legal advice before offering Clynx commercially.
 5. Windows installer is unsigned; no signed-update delivery; macOS never built. The installer in beta-release/ was built BEFORE the Phase 10 desktop changes - a new build is needed to ship them (not done; needs your go-ahead).
 6. The desktop's built-in default server address is still http://localhost:8787. Before shipping a cloud-enabled desktop, set the real address (the sign-in form now starts from the saved address, and people can type one under "Advanced").
 7. eBay application token cache is per server instance (fine for one instance; shared cache is a later improvement). AI spend reservations fall back to per-instance memory if Redis is down.
 8. Two-factor authentication is not implemented. Password reset links last 1 hour and verification links 24 hours (single use).
 9. The website's E2E suite uses system Chrome; CI installs nothing extra on Ubuntu runners (Chrome is preinstalled there) - the CI jobs have not been run on GitHub yet.
10. A single Owner is supported by design. Recovering a lost Owner requires shell access to the server (documented in cloud/DEPLOYMENT.md).

6. WHAT I FOUND AND FIXED WHILE TESTING (evidence the tests are real)
-----------------------------------------------------------------------
 - Parallel migration runs raced (added a Postgres advisory lock).
 - Refresh-token rotation had a race (now transactional with a per-user lock).
 - AI spend check was not atomic (now reserve-then-check).
 - Cached "latest release" hid a just-published release (no-cache).
 - A too-large release upload hung the connection (stream handling fixed).
 - eBay filter regex allowed angle brackets (tightened).
 - Blank values in a copied .env.prod (for example an empty BILLING_SUCCESS_URL or METRICS_TOKEN) made the server refuse to start; blank now means "not set".
 - The website build only worked because a Node type package happened to be installed; the Docker build exposed it (declared now).
 - Revoking a device from the website did not end the desktop's sign-in (fixed, section 2).
 - The desktop sign-in form ignored the saved server address (fixed).
 - AI narration quietly never ran for a signed-in account without its own key (fixed).
 - The deployment doc said EBAY_ENV=sandbox but the code compared with SANDBOX (now case-insensitive, doc corrected).
