3. HOW THE XBOX 360 CONTROLLER IS HANDLED NOW
---------------------------------------------
  Identification: the photo-analysis prompt now asks to keep "360"/"1403" in the name (unverified live). Whatever name comes back, the code
    comparison finds the codes 360 and 1403 in the title and not in the matched entry "Xbox Wireless Controller" -> "unconfirmed".
  Confidence: an unconfirmed listing gets confidence LOW; its evidence is capped at "weak" whatever the entry's sales count is. The Gate says why.
  Resale comparisons: the generic entry's $48 value is NOT trusted for it. Before an alert, Clynx prices a new entry named from the listing
    ("Xbox Wireless Controller 360 1403"); its search requires 360 and 1403, so Series/One/Elite comps are excluded; if the comps still mix versions
    they are split by price-separating words. The generic entry itself is not overwritten with the 360 numbers.
  Qualification: with the generic value it is "Worth a look" (visible, not pushed). Once the specific entry is priced it is judged on that price:
    at $15 not a deal (a 360 pad is ~$18), at $10 a deal. The thresholds and margin math are exactly the old ones.
  Also: a generic entry whose comps mix versions is flagged "approximate" and valued at the cheapest group (a floor), and the Discovery tab says so.

4. IS IT UNIVERSAL?
-------------------
  The NEW logic is category-independent by construction: codes are found by pattern (letters+digits, 3+ digit numbers), the price-split learns its
  separator words from the comps, and a test fails the build if brand/category words appear in src/main/identity/. It was exercised on Xbox, vehicles,
  tool batteries, appliances and collectibles (synthetic data I wrote).
  It is NOT yet fully universal, because:
   a. Old category-flavoured rules still run underneath and were left in place on purpose: the color list (colors.ts), the tier-word list (ti/xt/ultra/pro/
      oled..., compFilter.ts), the single-letter model rule (Series S/X), the accessory word list (controller/battery/charger/cable..., compFilter.ts),
      "console"-centric accessory-only phrases (scorer.ts), and the examples in the vision prompts (Elite Series 2, DualSense Edge). They cause no
      harm to other categories but also do not help them; Stage 5 is meant to replace them with learned data.
   b. The code check needs digits. A variant that differs only by WORDS (Ultra, Elite, One, Type R, Chase variant) is caught only where there are enough
      comps (6+) for the price-based split, not by the listing-vs-entry check.
   c. populations.ts has a small list of English filler words (a, the, used, new, shipping...). That is language-specific, not category-specific.
   d. The price split needs a price gap of 30% or more; products whose variants differ by less are not separated.
   e. Digits in the title that are not identity (an item number, "HEG-001") also trigger doubt (see weaknesses).

6. WHAT STAGE 3 WILL CHANGE IN THE DATABASE
-------------------------------------------
  Schema (additive only, same idempotent ALTER/CREATE-IF-NOT-EXISTS pattern the app already uses on every start; nothing rewritten at migration time):
    products:  identity_json TEXT, identity_key TEXT, identity_level TEXT  (all nullable)
    listings:  identity_json TEXT, product_match_level TEXT                (nullable; the existing product_id/matched_item stay as saved)
    NEW table product_aliases(alias_norm TEXT, product_id TEXT, source TEXT, confidence REAL, created_at INTEGER, PRIMARY KEY(alias_norm, product_id))
    NEW indexes on products(identity_key) and product_aliases(alias_norm).
  Behavior (all behind flags, off by default, switched on one lookup site at a time):
    - A resolver returns {product, level (exact/line/unknown), candidates, why} using best attribute agreement, not "newest first".
    - isSimilarProductName stays only as a cheap candidate generator; merges happen only when identity keys are equal or an alias/user merge says so.
    - Aliases are learned only from confident matches, are reversible, and never join entries whose codes conflict.
    - A listing's product link is written once with its confidence and no longer silently re-resolved on every save.
  Effect on existing products: NONE at migration. A background backfill (rate-limited, never at startup, so Phase 3 startup gains stay) fills
    identity_json/key from each entry's name, notes and the source titles of its photos. It only writes the new columns. Existing names, photos,
    notes, prices, Search For items, Watches and listing history are untouched. Splitting mixed entries is NOT part of Stage 3 (that is Stage 6).

7. RISKS
--------
  Data loss: Stage 3 is additive, so low; the real exposure is Stage 6 (splitting/moving photos and notes). Mitigation: nothing automatic at first,
    a "needs review" list, user approval, a backup table so any split is undoable, original rows kept.
  Incorrect merging: alias learning or key equality could join two products. Mitigation: never merge on name containment; never join entries whose
    defining codes conflict; every alias carries source and confidence and can be undone; start in shadow mode and compare against current behavior.
  Duplicate creation: stricter matching creates more entries (e.g. "Galaxy S21" vs "Galaxy S21 5G"), and the doubt rule can create specific entries
    per model code. Mitigation: aliases, the existing exact-word-set duplicate guard in addProductStub (kept), a cap on specific entries created per
    day tied to the WatchCount allowance, and a review list.
  Performance: lookups must stay as fast as the Phase 1 name index (an inverted index on identity values is planned, plus a 10k-entry benchmark);
    startup must not regress (backfill is background only; the Phase 3 startup benchmark is re-run). The slice-1 checks cost ~16 microseconds per product.
  Cloud sync: new fields stay local-only at first so older clients keep working; a versioned sync is a separate decision.
  Alert volume: more caution means fewer confident pushes in ambiguous cases; measure on a copy of your data before turning anything on.
