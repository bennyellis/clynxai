CLYNX DEAL QUALITY: ROOT-CAUSE INVESTIGATION
============================================
Read-only. No project code was modified. Everything below was traced in the current source (line numbers as of 2026-10-11)
and the main defects were REPRODUCED against the real modules with a throwaway script kept outside the project (output in
Appendix A). A small read-only copy of one account's listings database (22 rows) is used as supporting evidence only.

Companion document: DEAL_QUALITY_AUDIT.txt (broader audit). This one goes deeper on root causes, with code excerpts,
and on the canWithhold:false Watch path and post-scoring revalidation.


0. SUMMARY
----------
Poor-margin, months-old and low-quality listings reach BOTH the Feed and the phone for four independent reasons:

  (1) The age filter does not understand common Facebook phrasing ("a day ago", "a week ago", "a month ago",
      "about an hour ago") and treats anything it cannot parse, or cannot find, as FRESH. Two Facebook Watch routes
      skip the age gate altogether.
  (2) Several routes decide "deal" WITHOUT the deterministic margin rule: an AI opinion (Search For item with no
      reference price; General AI), a Watch match, and the photo-based hidden-gem estimate.
  (3) The only check just before a push is "could you haggle it down far enough?" It ignores margin, stars,
      evidence quality and age, treats "no data" as a pass, and is switched OFF for every Watch match
      (canWithhold:false).
  (4) There is no final gate and no revalidation. isDeal is decided once, is never revoked (not even when the push is
      withheld), and every screen reads it raw. A Watch match recorded early can never be retracted.

Fix in one sentence: one pure Deal Quality Gate, called at every producer of a "deal" or a profit-based alert, whose
verdict (deal / worth_a_look / pass, with reasons and evidence) is PERSISTED and used by the Feed, Best Deals and
notifications; Watch-match notifications stay a separate, explicitly labelled kind.


1. ROUTES: DISCOVERY -> FEED -> NTFY
------------------------------------
Everything saved by store.saveScored appears in Feed "All" (by earlier explicit request, including instant skips).
Feed "Deals", Dashboard Best Deals, "deals today", flame/glow styling and deal narration all key off isDeal.

Producer routes (file : function):

  A  Search For match            scrapeEngine.evaluateListing -> scorer.scoreListing (search branch)
  A2 Search For match, no value  same branch, falls into extractGeneralDeal (AI), still tier "search"
  B  Database title match        scoreListing (valueForTitle branch), tier "search"
  C  General AI                  scoreListing (extractGeneralDeal), tier "general"
  D  Facebook Watch, passive     evaluateListing -> recordWatchMatchesIfAny  (called BEFORE vision and again after)
  E  Facebook Watch, active      runWatchCheck -> evaluateWatchCandidate -> scoreListing -> recordWatchMatchesIfAny
  F  eBay (A/B/C scoring)        ebayEngine main loop -> scoreListing
  G  eBay Watch                  ebayEngine.recordWatchMatches
  H  Post-score promotions       runPostScoringPipeline: green-flag promotion, hidden gem / bundle (can set isDeal)

Notification routes (3 call sites; all go through preAlert.prepareAlert, but with different settings):

  deal alert (main)    scrapeEngine.ts:2350-2372  if (scored.isDeal) -> prepareAlert(canWithhold:true) -> sendDealAlert
  deal alert (eBay)    ebayEngine.ts:361-382      same, canWithhold:true
  Watch alert (FB)     scrapeEngine.ts:1063-1135  recordWatchMatchesIfAny -> prepareAlert(canWithhold:FALSE) -> sendWatchMatchAlert
  Watch alert (eBay)   ebayEngine.ts:406-455      same, canWithhold:FALSE

The two kinds are not distinguishable in content: both use summary.title ("<square> $price - product - Listed X ago")
and "reason - stars". The Watch alert differs only by an ntfy tag ("eye" vs "moneybag") and, for a Watch with its own
ntfy topic, the destination. A listing that is both a deal and a Watch match is pushed twice.


2. WHERE EACH RULE CAN BE BYPASSED
----------------------------------
Rule: MINIMUM PROFIT MARGIN (default 20% of what the user keeps)
  - A2 (AI, no reference value)          never computed                          [D6]
  - C  General AI                        never computed                          [D7]
  - D/E/G Watch                          never computed; Watch has its own optional $/% conditions  [D4, D5]
  - H  hidden gem via photo lump         computed, but on an AI-guessed, uncapped extras value  [D9]
  - preAlert                             not re-checked (reach test only)       [D10]
  - A/B (priced)                         enforced, except "within max price AND reachable" counts at asking margin < min  [D13]

Rule: MAXIMUM LISTING AGE (default 24 h)
  - any route, unparseable phrase        fail-open                               [D1]
  - any route, no age text               fail-open                               [D2]
  - E Facebook Watch, active             no post-detail age check at all         [D3]
  - D Facebook Watch, passive            a Watch with no age limit "rescues" an old listing into normal deal scoring  [D3]
  - eBay                                 enforced with a reliable timestamp (not a bypass)

Rule: NEGOTIATION LIMIT (default 15% off asking)
  - A2, C, Watch routes                  not applied
  - everywhere else                      applied only as "reachable" in A and in preAlert; null (no data) passes  [D10]

Rule: VALUATION CONFIDENCE / EVIDENCE
  - store value SQL has no minimum sample, no staleness check, no basis check; scorer hard-codes confidence "high"  [D8]
  - Watch reference price may be other sellers' asking prices                       [D5]
  - extras valued by one AI guess                                                    [D9]


3. CONFIRMED DEFECTS
--------------------

D1. AGE PARSER FAILS OPEN FOR "a day ago", "a week ago", "a month ago", "about an hour ago"      [CRITICAL]
  File/function: src/main/listingAge.ts : estimateListingAgeHours (14-33) and isListingTooOld (46-54)
                 text source: src/main/scraper.ts : extractListingAge (1272)
  Code:
      const match = text.match(/^(\d+)\s*(minute|min|hour|hr|day|week|month|year)s?\b/);
      if (!match) return null;                       // "a week ago" lands here
      ...
      export function isListingTooOld(ageText, maxHours = 24) {
        if (!ageText || maxHours === null) return false;
        const hours = estimateListingAgeHours(ageText);
        return hours !== null && hours >= maxHours;   // null => "not too old"
      }
  Pathway: Facebook detail page text ("Listed a week ago in Dover, DE") -> extractListingAge -> evaluateListing
           (scrapeEngine.ts:1572-1577) -> isListingTooOld -> false -> the listing is scored as fresh.
  Root cause: the regex requires a digit; Facebook also writes "a/an <unit> ago" and "about/over/almost ...". The
           function then deliberately treats "can't tell" as "keep".
  Evidence: Appendix A R1 (a day / a week / a month / about an hour / over a year ago all return "too old? false").
           In the sample DB: 8 of 22 listings had such a phrase, 4 of them saved as deals (one an Xbox "a week ago").
  Fix: accept a/an/one/about/over/almost/more than + unit (and "x and a half" forms); return a three-state result
       (fresh | stale | unknown) instead of a boolean; never let "unknown" qualify a listing as a deal (see gate).

D2. A MISSING AGE IS TREATED AS FRESH                                                                [HIGH]
  File/function: listingAge.ts : isListingTooOld (line 47 "if (!ageText ...) return false"); scraper.ts : extractListingAge
                 returns null when no "Listed ... ago" is on the page.
  Pathway: any Facebook listing whose page layout/text differs -> listingAge null -> gate skipped.
  Evidence: 2 of 22 sample listings have no age; one is a saved general-tier deal.
  Fix: unknown age is a first-class state; persist parsed hours (listing_age_hours) and the parse source; unknown
       can be shown ("worth a look") but never promoted to a deal or pushed as one.

D3. FACEBOOK WATCH ROUTES DO NOT ENFORCE THE GLOBAL AGE CAP; A WATCH CAN "RESCUE" AN OLD LISTING INTO NORMAL SCORING   [HIGH]
  File/function: scrapeEngine.ts : evaluateListing (1573-1577) and evaluateWatchCandidate (3294-3340)
  Code (passive route D):

        if (w.maxListingAgeMinutes === null) return true;          // a Watch with NO age condition always rescues
        return listingAgeHours !== null && listingAgeHours < w.maxListingAgeMinutes / 60;
      });
      if (isListingTooOld(detail.listingAge, config.maxListingAgeHours) && ageQualifiedRescueWatches.length === 0) { ...skip... }
      // a rescued listing falls through to seller risk, scoreListing, hidden gem, deal alert...
  Code (active route E): evaluateWatchCandidate never calls isListingTooOld. The only age control is Facebook's own
      "Date listed" filter applied best-effort inside searchMarketplace (scraper.ts:278; runWatchCheck passes
      watch.maxListingAgeMinutes or the global value at scrapeEngine.ts:3213). If the control cannot be clicked, the
      engine logs and continues unfiltered; there is no post-detail backstop for Watches.
  Root cause: the rescue was written so a Watch with a LOOSER window than the global one could still be evaluated, but
      the rescued listing then continues through the ordinary deal pipeline, where nothing re-checks age (the code
      comment says so). Route E has no age check.
  Evidence: the sample DB contains a saved deal "Xbox series X, 4 days ago" under a 24 h cap (no watches remain in
      that copy, so I cannot prove which of D/E produced it; no other route skips the gate).
  Fix: let the Watch evaluate the listing AS A WATCH MATCH only; the standard deal path must still require the global
       age rule (the gate). Add the post-detail age check to route E (Watch-specific window, else global).

D4. WATCH ALERTS ARE UNCONDITIONAL (canWithhold:false), AND A WATCH MATCH IS NEVER REVALIDATED                [HIGH]
  File/function: scrapeEngine.ts : recordWatchMatchesIfAny (1063-1135); ebayEngine.ts : recordWatchMatches (406-455);
                 watchMatching.ts : evaluateWatchConditions (133-162); store.ts : recordWatchMatch (2466)
  Code:

  Pathway: any title-matching, price-qualified listing -> satisfied=true -> push, regardless of age, margin, loss,
           evidence, stars. prepareAlert still runs, but canWithhold:false means its verdict is only used to write the
           message.
  Root cause: Watch was designed as "tell me about this product", so every quality rule was bypassed rather than
           being labelled. The alert is formatted exactly like a deal alert (stars included), so a 1-star loss reads
           as a recommendation.
  Revalidation gap: recordWatchMatchesIfAny runs at TWO points (before vision, scrapeEngine.ts:1739, and after bundle

  Fix: keep Watch notifications (that is their purpose) but as their own kind with the gate verdict attached (see

4. THE CENTRAL DEAL QUALITY GATE (PROPOSED, NOT IMPLEMENTED)
-----------------------------------------------------------
One pure function, no I/O (suggested file: src/main/dealGate.ts):

    qualifyListing({
      scored,                  // final scored listing (after all promotions)
      evidence,                // ValueEvidence: valueUsd, basis, sampleSize, ageDays, matchQuality (null if none)
      age,                     // { state: "fresh" | "stale" | "unknown", hours | null }
      settings,                // net %, min margin %, max cut %, max age hours, strictness
      extras,                  // counted extras: { usd, corroborated, estimated }
      vision,                  // { matchesClaim: true | false | null, confidence }
      pathway,                 // "search" | "database" | "general" | "ebay"
    }) -> {
      status: "deal" | "worth_a_look" | "pass",
      stars: 1..5 | null,
      reasons: [{ code, severity, text }],
      facts: { valueUsd, basis, sampleSize, compAgeDays, ageHours, ageState,
               profitAtAskUsd, marginAtAskPct, cutNeededPct, extrasUsd, extrasEstimated }
    }

Decision rules (all deterministic; thresholds configurable, suggested defaults):

  PASS (hard):    placeholder price; age stale (>= max age); photo mismatch confirmed; hard price cap exceeded;
                  margin below minimum AND cut needed above the limit (existing rule).
  WORTH A LOOK:   age unknown; no value evidence (AI-only finds: D6, D7); evidence thin (fewer than 3 sales, or
                  ask-only basis, or comps older than 14 days: refresh first, then re-evaluate); match quality low;
                  extras uncorroborated/estimated/uncapped (D9); stars below 3; margin at asking below minimum
                  but within the haggling limit with weak evidence.
  DEAL:           fresh age, solid evidence, margin at asking >= minimum (or within haggling limit with strong evidence,
                  shown as "needs N% off"), stars >= 3, vision not contradicting.

Everything that decides "deal" or sends a profit-based alert must call it:
  1. scrapeEngine.runPostScoringPipeline  after the hard-cap block (about line 2209) and before the alert (2350).
  2. ebayEngine main loop before its alert (361).
  3. preAlert.prepareAlert  with the FRESH market value; if the fresh value demotes the listing, write it back (D11).
  4. Watch evaluation (scrapeEngine.recordWatchMatchesIfAny, ebayEngine.recordWatchMatches), to attach the verdict.

Persistence: add columns deal_status, gate_reasons (JSON), gate_stars, listing_age_hours, value_basis, value_sample.
Feed "Deals" = deal_status = 'deal'; add a "Worth a look" filter; Best Deals, counters, flame styling, narration read
deal_status. Show the reason on the card ("Needs 12% off asking", "Only 2 sales to go on", "Age unknown").

5. KEEPING WATCH-MATCH NOTIFICATIONS SEPARATE FROM QUALIFIED-DEAL NOTIFICATIONS
-------------------------------------------------------------------------------
  - Two explicit notification kinds:
      QUALIFIED DEAL   only when gate.status = deal. Title prefixed clearly; stars and "why".
      WATCH MATCH      always delivered (that is what a Watch is for), titled "Watch match: <name>", carrying the
                       gate verdict as plain text ("Not a qualified deal: age unknown, only 2 sales"). canWithhold:false
                       stays, but its meaning becomes "deliver", not "deliver as if recommended".
  - A listing that is both: ONE push ("Watch match + qualified deal") instead of two.
  - Watch matches count as "Deals" in the Feed/Best Deals only if they also pass the gate.
  - Watch matches are evaluated once, after the final scoring step, so the age/stars/evidence attached are final; a
    later demotion downgrades the stored match (does not delete it).
  - Watch profit figures use only eBay-based references (D5).

6. PROTECTING DISCOVERY OF UNUSUAL / UNDERVALUED PRODUCTS (RECALL)
-----------------------------------------------------------------
  - "Worth a look" is a visible Feed state, not a discard: thin evidence, unknown age, AI-only finds and uncorroborated
    extras stay discoverable; only the push and the "Deal" label are withheld.
  - AI-only finds trigger Database research for that product so the next listing is priced deterministically.
  - Hidden gems keep their path (item-by-item breakdown, then lump fallback) with caps/corroboration; failing that they
    show as "worth a look: possible hidden gem".
  - Unknown-age listings are shown, not hidden.
  - A "Strict quality gate" setting (default on) lets power users loosen evidence rules (for example accept 2 sales).
